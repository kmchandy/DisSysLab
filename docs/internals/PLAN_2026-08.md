  persistent, concurrent app.* The force of it comes from n > 1 — ten traders

# Item 1 — the foundation skill, in detail

## What it is

`skills/office-builder/` — the skill that turns "I want to watch X and do Y" into
a running office, for someone who has never seen the framework. It is the
office-builder, the student enabler, and the root of the skills tree; the
trading and (eventual) drug-discovery skills build on it.

## Shape

Following the pattern the three existing skills already validated — the only
thing ever bundled is the check; everything executable stays in the library:

```
skills/office-builder/
├── SKILL.md
├── scripts/
│   └── check_office.py        # thin CLI over dissyslab.office.check_wiring
└── references/
    ├── office_grammar.md      # the office.md sections and sentence forms
    ├── sources_and_sinks.md   # pointer + condensed catalog
    └── worked_examples.md     # 3–4 offices, each with its role files
```

The analysis logic goes in **`dissyslab/office/check_wiring.py`**, not in the
bundle — but note this *departs* from the house convention rather than
following it. The bundled `check_no_lookahead.py` turns out to be 559 lines
and fully self-contained, importing nothing from `dissyslab` except in a
`__main__` demo block. So the convention is: **self-contained where
self-containment is cheap.**

It is cheap there and not here. `check_no_lookahead` receives a *function* the
user wrote and needs no framework internals. `check_wiring` must parse
`office.md` and resolve role names against four registries; reimplementing that
standalone would duplicate the parser and drift within a release. So: library
module, thin runner in the bundle — for a reason, not by inventing a shape.

**Status: written and passing.** See "Results" below.

## What SKILL.md has to carry

1. **The office.md grammar** — Sources / Sinks / Agents / Connections, the
   sentence forms, and the two outport spellings a source accepts
   (`destination` and `out` are both legal; say so, since the generator's own
   error message explains this at length).
2. **When to write an English role vs a Python role.** The existing rule of
   thumb — English when the judgment is linguistic, Python when it is
   deterministic, cheap, or numeric — with examples.
3. **The component catalog**, condensed, with a pointer to
   `docs/SOURCES_AND_SINKS.md` for the full list.
4. **The build loop**: draft `office.md` → run the check → fix what it reports
   → `dsl run` → read the per-agent message-count summary.
5. **An explicit instruction to run the check before running the office**,
   and to report what it found rather than silently repairing — the student
   should see the fault, since the fault is the lesson.

## The check — what it does that nothing else does

Local checks already exist and must not be duplicated. `Network.check()`
verifies block-name uniqueness, that ports named in connections exist, that
declared external inputs/outputs are wired, and that no connection points at a
missing block. The parser reports syntax errors with file, line, and snippet.
`from_officespeak.py` raises `GeneratorError` at twelve sites for kind-specific
constraints (a `merge_synch` with no declared inports, a `select` with a
command port and no data inports, a `gate` without exactly its required
inports, a source using the wrong outport spelling, and so on).

All of those are **local** — they check one statement or one agent. What is
missing, and what generates almost every beginner hang, are **global graph
properties**. Those are the check's job:

| ID | Fault | Why it matters |
|---|---|---|
| W1 | **Unfed inport** — a declared inport that no connection writes to | The agent blocks on first receive, forever. This is *the* beginner hang. `Network.check()` confirms ports named in connections exist; nothing confirms every declared inport is named in some connection. |
| W2 | **Unread outport** — an agent sends where nothing receives | Output silently vanishes; the student sees an office that "does nothing." |
| W3 | **Unreachable agent** — no path from any source | Usually a typo in a name that happens to be legal elsewhere. |
| W4 | **Dead end** — an agent whose output reaches no sink | The work is computed and discarded. |
| W9 | **Connection names something that isn't there** | The compiler catches this too, but catching it here means one report listing everything, not one error per run. Pairs with W3 — a misspelling produces both, and the pair tells the story. |
| W6 | **Missing role file** — `X is a topic_tagger` with no `roles/topic_tagger.md` or `.py` | Fails late and confusingly today. |
| W7 | **Cycle with no exit** — a loop no `gate` or terminating condition can break | *Informational, not an error.* Cycles are legal and intended. Report it and say why it may not terminate. |
| W8 | **Source with no destination / sink with no feeder** | Trivially wrong, trivially caught. |

## What static analysis cannot see — and why that matters

An earlier draft of this plan claimed the check could catch the shape of bug
#47 — a coordinator blocked on one inbox while another holds a message it will
never read. **That was wrong.** In #47 every port is wired and messages flow;
whether the buffered message is ever readable depends on how many messages
each source happened to produce and how they paired up. That is an execution
history, not a property of the org chart. No static analysis reaches it. It is
a deadlock, and it belongs to item 2.

Bug #47 is therefore the best argument *for* item 2, not evidence for item 1 —
it is the case that proves structural checking is insufficient.

Two consequences worth keeping:

- **W1 and W2 are narrower than they look.** For most agents written in
  `office.md`, ports are *inferred from the connections themselves* — a
  synchronizer's inports are whatever gets wired to it — so a "declared but
  unwired" port cannot arise. W1/W2 are meaningful only for roles with an
  intrinsic shape (a Python role declaring its ports, or a built-in kind such
  as `gate` that requires specific ones). Implemented as a later pass, not
  half-way now. In practice the fault still surfaces through W4: deleting the
  wire into a synchronizer's port makes its feeder a dead end.
- **The static/dynamic boundary is course material.** What you can know from
  the org chart versus what you can only know from an execution is a real
  distributed-systems lesson, and a first-year meets it here, concretely,
  rather than as an abstraction.

## Output

The output is the whole point, so it is specified rather than left to taste.
Report every fault found — not the first — grouped by agent, each naming the
agent, the port, and the repair. Plain text, no traceback:

```
check_office: my_office/office.md — 2 problems, 1 note

  W1  Sync (synchronizer) inport 'location' is never written to.
      Sync will block on it forever. Declared inports: entities,
      severity, topic, location. Written to by: Eve, Sam, Tom.
      Nothing connects to 'location'. Did you mean to wire Greta?

  W6  Greta is a 'geolocator', but neither roles/geolocator.md nor
      roles/geolocator.py exists.

  W7  note: Riley -> Sasha -> Eve -> Riley is a cycle. Cycles are
      legal, but this one has no gate, so the office will not
      terminate on its own.
```

Exit non-zero if any W1–W6 or W8 fires; zero on notes alone.

## Acceptance

1. **Every one of the ~31 gallery offices passes clean.** That is the
   regression test, it is free, and if any of them fails the check is wrong
   (or the office is, which is worth knowing).
2. **Deliberately break four of them** — delete a connection to a
   synchronizer inport, misspell an agent in `Connections`, remove a role
   file, orphan an agent — and confirm each is reported with the right ID and
   a repair the student could act on.
3. **One first-year-shaped trial**: someone who has not seen the framework
   describes an office to an agent with the skill loaded, and gets to a
   running office without a hang they cannot explain.

## Results — first run, 2026-08-17

Against the 20 offices in the published package (the repo has ~31; the rest
are unreleased):

- **First run: 8 clean, 12 failing.** All 12 were false positives from role
  resolution — roles resolve against four surfaces, not one: the office's own
  `roles/`, the shipped `dissyslab/roles/` (15 English prompt roles), the
  `fn_lib.FN_LIB` registry, and the library's `<name>_role` coordinator
  factories. Fixed.
- **Second run: 16 clean, 4 failing — and all 4 are real.**
  `stocks_monitor`, `weather_monitor`, and `kalshi_market_watch` each declare
  a `jsonl_recorder` sink that no connection ever writes to;
  `wardrobe_assistant` declares an unfed `discard`. **Corroborated on disk:**
  `stocks_monitor.jsonl`, `weather_monitor.jsonl`, and
  `kalshi_market_watch.jsonl` are all 0 bytes in the working tree. The check
  found a real, repeated bug in the shipped gallery on its first honest run.
- **Negative tests pass.** Four deliberate breaks on `situation_room` — a
  misspelled agent in `Connections`, an orphaned agent, a removed wire into
  the synchronizer, a removed wire to the sinks — each reported with the right
  code and an actionable repair.

**Known rough edge:** deleting the last connection to the sinks reports seven
separate W4 dead ends, one per upstream agent. Correct, but for a first-year
that is worse than one message. Report the cascade frontier rather than every
node. Next refinement.

## Honest scope

- The check is static. It cannot see a role that never sends to `out`, or an
  LLM role that returns the wrong shape at runtime. Those are item 2's job.
- It cannot see deadlock. See "What static analysis cannot see" above.
- W7 cannot always tell a terminating loop from a non-terminating one. It
  reports the cycle and the absence of a gate, and says so; it does not decide.
- The skill is useless without `pip install dissyslab`. That is already true of
  `paper-trader` and is accepted, but it should be stated in SKILL.md rather
  than discovered.

# Items 2–4, briefly

**2. Runtime hang diagnosis.** When an office hangs, say which agent is
blocked, on which port, and what would have to arrive for it to proceed —
a wait-for graph and cycle detection over it. Its customer is the confused
first-year, not a trader; the trader's book does not deadlock. It is also
legitimate course content, met at the moment the student's own app hangs.
Note that **deadlock detection is not implemented today** — it appears in
`architecture.md` and `common_gotchas.md` as prose and in no Python.

**3. Office-per-process.** Design is done and not re-derivable cheaply:
`docs/internals/process_parallelism_decision.md` (why per-agent was scrapped;
three diagnosed faults) and `docs/internals/process_per_office_design.md` (one
office, one process; composition expressed as an `office.md` whose agents are
offices). Estimated at about a week in those docs. Two payoffs: it makes
"distributed" honest, and — per the design doc — a network of offices may
contain cycles, so end-of-stream sentinels do not suffice and real distributed
termination detection becomes *required* rather than illustrated. That is the
difference between a course that describes an algorithm and one that runs it.

**4. Cowork skills for on-ramp apps.** Two or three, chosen as the places a
student starts — not all 31. Wrapping the gallery wholesale was evidence
surface for a paper that is no longer happening, and it is the layer where
this project competes worst.
