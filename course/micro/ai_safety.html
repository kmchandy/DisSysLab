Power and Safety

Systematic methods for reasoning about system behavior

In this course you build systems of multiple cooperating agents. Much of the course deals with how you specify multi-agent systems using a simple temporal logic (UNITY) and how you use logic to reason about system behavior. You will also develop test suites tailored to the code that you write.

The power and flexibility of AI

You will also build multi-agent systems in which some agents use language models; we call such agents "AI agents." You describe what you want an AI agent to do in English. English is ambiguous and you may not be able to predict what an AI agent will do. Telling an agent what to do in English takes less time than specifying its behavior, writing code, and demonstrating correctness.

AI in persistent, sense-and-respond systems

AI safety is especially important in persistent systems that sense and respond to changes in the environment. These systems run in the background forever. An agent may behave in a problematic way for a long time before problems are discovered. AI systems can search the web and learn new ways of interacting with the environment. They can modify the environment and evolve as the environmental changes. This is powerful, but also potentially unsafe.

The fundamental dilemma

On one hand we want to specify systems precisely and use systematic methods to demonstrate that systems are safe. On the other hand, we also want the immense power and flexibility of AI. This tension between predictability and power informs the framework we use and the programming conventions we adopt.

Distributed system and office

We use the phrases "distributed system," "multi-agent system," and "office" interchangeably. The office is a metaphor for a distributed system with worker in the office representing agents in the system.

SECTION 1 The choices we made in the power-safety tradeoff

We use UNITY, coupled with its rely-guarantee proof technique, to reason about systems, including systems with AI agents. We assume that an AI agent's behavior satisfies a specification without proving that it does. Then we prove properties about the ensemble, relying on agents obeying their specifications. The problem with the method is that AI agents may not behave as specified; so the ensemble may not either. The benefit of the method is that we gain the power of AI while we circumscribe its unpredictabilty.

Fundamental features of all distributed systems

All distributed systems have components -- such as routers -- that agents use to communicate. We implemented these components ourselves rather than asking AI assistants to build the entire system from scratch for each new application. And we use logic to specify and reason about these components

Distributed systems have operations such as distributed termination detection, global snapshots, deadlock detection, and recovery from transient errors. We implemented these algorithms ourselves, and we reason about the algorithms using logic. We chose not to ask AI assistants to implement all these features for each new distributed app.

Restricting interaction with the environment

The set of external devices - websites, sensors, actuators, files -- with which the system communicates is fixed. You specify the set when you create the system. The system cannot cause havoc by sending messages to arbitrary devices.

Checking the messages into and out of an agent

You cannot inspect the code that implements a language model; however, the framework gives you a mechanism -- a guard -- which allows you to specify predicates on messages that enter and leave an AI agent. Consider a language model that gives a sentiment score between -1.0 and 1.0 for each message. You may not be able to predict the score that the model will assign to an arbitrary message. You can, however, check that the score is in the specified range.

SECTION 2Programming conventions that we adopt

We follow these conventions.

  1. Remember that the output of a language model is unpredictable. Design so that an output by one agent does not cause the entire system to fail .
  2. Never put confidential information into a conversation with an LLM. No passwords, no financial details, no API keys, nothing you would not be willing to see stored.
  3. Do not gather information that is private to others. No sensors that capture other people's private information, no sources private to someone else. A microphone is harmless until it accidentally records a private conversation.

Following these conventions makes your office safer but not perfectly safe.
