SECTION 1A model of a distributed system

An office is a set of agents and a set of connections. Each agent runs in its own thread of execution, and each agent has its own private state. Agents share no memory. The only way in which agents can interact is that an agent can send a message to another agent.

Inboxes and outboxes. Each agent has a set of inboxes and a set of outboxes. Inboxes and outboxes are queues of messages. An agent receives messages from its inboxes and puts outgoing messages in its outboxes. A source agent is one with no inboxes, and a sink agent is one with no outboxes.

Connections: message channels. A connection is a message channel from an outbox of an agent to an inbox of an agent. A connection is specified by a 4-tuple: sending agent, sending agent's outbox, receiving agent, receiving agent's inbox. Each message channel is a queue of messages. The words connection and channel are used interchangeably throughout.

Message propagation. The system removes a message from a nonempty outbox and puts a copy of the message in every channel to which that outbox is connected. The system also removes a message from a nonempty channel and puts the message in the inbox to which the channel is connected.

Agent Actions. We first describe actions for agents other than sources and then describe source actions. An agent waits to receive messages from exactly one of its inboxes. If that inbox is empty then the agent does nothing, and continues waiting for a message in that inbox. If the inbox is not empty then the agent removes a message from the inbox and processes it. While it is processing the message the agent may put messages on its outboxes. The processing of a message always terminates. After the message is processed the agent waits again for a message from an inbox, possibly a different one.

Source Actions. A source receives messages from an external message source such as a social media stream — not through an inbox, since a source has none, but from outside the office. When the external source generates a message it is processed by the source, which puts messages on the source's outboxes.

Sink Actions. A sink removes a message from its inbox and sends messages to external devices such as actuators, databases, or files.

SECTION 2Model of Computation

We will reason about the correct behavior of a distributed system using UNITY logic which is a simple fragment of temporal logic. The model of computation in UNITY is as follows. A program is a set of actions and an initial state. Computation proceeds by executing any action in the set. Actions are selected nondeterministically and every action is executed eventually.

Consider a computation with actions x and y. A computation can proceed by selecting either x or y, for example a computation could be x, x, x, y, x, .... The requirement that every action is executed eventually means that there is no infinite computation that stops executing an action after some point. For example there is no computation that stops executing y after executing N actions for any N. The requirement that every action is selected eventually is called a fairness requirement.

Actions. The system has three types of actions: agent, outbox, and channel actions. A computation proceeds by selecting any agent, outbox or channel and executing its action.

  1. Agent action If the inbox for which the agent is waiting is empty then the action is a skip -- do nothing -- else remove a message from the inbox and process it.
  2. Outbox action If the outbox is empty then skip else remove a message from the outbox and put copies of the messages in all the channels to which the outbox is connected.
  3. Channel action If the channel is empty then skip else remove a message from the channel and put a copy of the message in the inbox to which the channel is connected.

A source agent is treated like any other agent -- the action is if there are no messages from the source to be processed by the agent then skip else take one message from the source and process it.

Terminated state: What is the computation after the system reaches a terminated state in which sources have stopped and all channels are empty? The computation continues forever, even from a terminated state, but every action is a skip and so the state doesn't change. It's convenient to assume that computations are infinite though distributed systems deal with termination.

SECTION 3Correctness and Performance

In this course, the specification of a distributed system does not include anything to do with time or performance. You can see why the use of a weak model of computation -- execute any action -- without any mention of time limits what we can prove about systems.

In practice, we are concerned about performance too; however, performance depends on the underlying programming language and operating system. We won't prove performance properties but we will discuss likely behavior.

An example of how we treat performance is a type of agent called an alarm. An alarm has an inbox and an outbox; its action is to remove the message from the inbox, wait for a time specified in the alarm, and then send a message on the outbox. The wait time can be any value -- we assume that the implementation attempts to wait for the specified time but we don't rely on it. So, when we reason about correct behavior we specify the action of an alarm as: Remove a message from the inbox and put a message on the outbox without mentioning the time interval between the steps.

SECTION 4Four things to do with it

Do these now, in the figures above — Tasks 1 to 3 in Figure 2 and Task 4 in Figure 5. Each takes a minute, and each is a fact you will use in a proof later. Answer before you open the reveal; guessing and being wrong is worth more here than reading the answer.

Task 1 · Prediction

In Figure 2, press Step five times. Before each press, say out loud which message will move and where it will go. Then say which action will fire next.

What you should have found

The first prediction is easy: given an action, the message that moves is determined — it is always the head of a queue, and it always goes to the tail of the next one. The second prediction is impossible. You can know what each action does and still not know which one happens next. Distributed systems are exactly this: local behaviour that is completely determined, composed into a global behaviour that is not.

Task 2 · What does X know?

In Figure 2, set connection takes from the outbox to 0. Watch X's outbox fill up and stop. Now answer: at that moment, what does X know about Y?

What you should have found

Nothing. X knows its own outbox is full. It does not know whether the connection is slow, whether Y is slow, whether Y is running at all, or whether every message it ever sent has already been read. A full outbox is consistent with all of those. An agent's knowledge is the contents of its own boxes and nothing else — and that single sentence is the reason the algorithms in this course are hard rather than obvious.

Task 3 · Can a message overtake another?

In Figure 2, try to get m5 into Y's inbox before m4. Use any combination of the sliders and Step you like.

What you should have found

You cannot. Every stage is first-in-first-out, so order is preserved along one connection. Be careful about how far that generalises: it is a property of this connection, not of the office. If X reaches Y by two different paths, or two agents both send to Y, nothing whatever is guaranteed about the order in which those messages arrive. Almost every wrong intuition about distributed systems is this local guarantee being quietly promoted into a global one.

Task 4 · Make an agent wait for ever

In Figure 5, wait until the agent is waiting on U, then set messages arriving at U to 0 and leave V running. Watch for half a minute. Now answer two questions: is the agent broken, and is anything in its own state different from a moment ago?

What you should have found

The agent is doing exactly what it was told: waiting on one inbox for a message that is not going to come. Nothing in its state is wrong, nothing is different from any other wait, and V goes on filling. This is the shape of almost every office that hangs — not a crash, not an error, but an agent correctly waiting for something that will never arrive. Notice also that you can see the problem only because you can see both inboxes at once. The agent cannot. Neither can any other agent.

SECTION 5Four facts, which are really axioms

Section 1 stated the model; the four tasks let you watch it. These four facts are what you should now have seen, and they are the form in which the model gets used. Write them down: everything later in the term is derived from them, and when a proof feels like magic it is usually because one of these was used without being named.

  1. Every message is somewhere definite. A message is in exactly one outbox, one connection, or one inbox, and nowhere else. Broadcast is the one thing that makes more of them: an outbox connected to two channels yields one copy in each, and from that moment they are two messages with two independent fates. Nothing is ever shared, and no message is in two places at once.
  2. Messages on one connection keep their order. Per connection. Not across connections, and not across paths.
  3. There is no clock the agents share. Each action happens when it happens. "At the same time" is not a statement you are entitled to make about two different agents.
  4. An agent knows only what is in its own boxes. It cannot see inside a connection, and it cannot see inside another agent. Anything else it wants to know, it must be told — by a message, which is subject to axioms 1 to 3.

SECTION 6The picture is the code

That was not an analogy. The picture is what the framework runs, and the framework will print it back to you. An office is described in a file of English called office.md:

# Office: my_first_office

Sources: hacker_news(max_articles=10, poll_interval=600)
Sinks: console_printer

Agents:
Alex is an analyst.

Connections:
hacker_news's destination is Alex.
Alex's briefing is console_printer.

Each line under Connections is one instance of the picture you just played with — a named outbox, three queues, a named inbox. Ask the framework to draw it and that is literally what it prints:

$ dsl draw my_first_office
hacker_news  destination ──▶ in_  Alex
Alex         briefing    ──▶ in_  console_printer

Two connections, two copies of the animation, running at once and independently. An office of forty agents is the same picture forty times. There is nothing else in the model.

Task 5 · Run it

Make yourself a copy, look at it, and run it:

$ dsl init my_first_office my_office
$ dsl draw my_office     # the picture
$ dsl check my_office    # is the wiring sound?
$ dsl run my_office      # watch messages move

Open my_office/office.md and my_office/roles/analyst.md and satisfy yourself that you can point at the outbox named briefing in both files, and at the connection it feeds.

Task 6 · Break it on purpose

In office.md, change Alex's briefing is console_printer. to Alex's summary is console_printer. and run dsl check again. Read what it says. Then put it back.

Notice which kind of mistake that was: it is wrong in the structure, so it can be caught without running anything. Hold on to that distinction — you are about to meet a mistake that cannot be.

SECTION 7Now the question

Here is the office of Figure 2 again, frozen. X's outbox is empty. Y's inbox is empty. Both agents have finished everything they were given.

Your office is running. You would like to know whether it has finished, so that you can print the results and stop. No agent can see the whole system — axiom 4 — so you do the obvious thing and ask each agent whether it is idle. Press the button.

Every agent is idle. Every agent's answer is true. The office is not finished.

The message is in the connection: the one place in the model that belongs to no agent, and that no agent can inspect. The predicate you actually needed is not every agent is idle. It is:

every agent is idle   AND   every connection is empty

and the second conjunct mentions exactly the state that no agent has access to. That is not a detail of this framework. It is a property of the model, and it would be true of any system built on axioms 1 to 4.

It gets worse, and the second problem is sharper than the first. Suppose every connection is empty. You still have to ask the agents one at a time, because asking is itself a message. Ask X at 10:00 — idle, true. Ask Y at 10:01 — idle, true. Between those two moments Y may have sent X a message and X may have gone back to work. Both answers were true when given. Their conjunction was never true of any single state of the office.

You cannot photograph a system whose parts are all still moving by photographing them one at a time.

Two of this term's central algorithms are answers to that sentence. Termination detection answers "has it finished?" without a global observer. The distributed snapshot answers "what state was it in?" without ever stopping it — and the reason a snapshot algorithm is subtle at all, rather than being four lines of code, is precisely that it must record the contents of the connections. Look at the picture again. That is where the difficulty lives, and you can see it.

There is a postscript worth having. Getting termination detection wrong does not produce a wrong answer; it produces an office that runs for ever. That happened in this framework: an agent's thread ended without reaching the shutdown protocol, detection waited for an agent that was gone, and the whole office hung. dsl check was silent, and correctly so — the wiring was fine. It was a fact about the execution, not about the structure. You met that boundary in Task 6.

Where to get answers without asking anybody

You are welcome to use an AI assistant in this course, and it will be wrong about this framework in ways you cannot detect, because it has read a thousand others. These four commands answer from your own installation, which is the version you are actually running:

dsl grammar     # what office.md is allowed to say
dsl roles       # every role that ships, and what it emits
dsl checks      # every structural fault check knows how to find
dsl doctor      # what is installed, and whether it is stale

A habit worth forming this week: when an assistant tells you something about an office, ask it which command it read that from. If it cannot say, it did not read it.
