Lab: building distributed systems

In the first class you built an office. This one is about the rest of what is in the box. Seven things, each with something to do at your own machine, and each chosen because it is the difference between an office that works and an office you would be willing to leave running.

Two of them also pay off later. The next two classes are theory — how to reason about a system when there is no clock any agent can read — and the last thing in this class is how to make DisSysLab show you your own system's records and its own global snapshots. You will be reasoning about your own office rather than mine.

1. The agent zoo, by what it does to the message

Every agent has inboxes, outboxes and a worker. What distinguishes the kinds is what the worker does to a message, and the built-in roles fall into five families. dsl roles prints the live list from your install, with the field each one adds.

familywhat it does
annotatorsadd one field and always send to out — topic_tagger, category_classifier, severity_classifier, urgency_classifier, sentiment_classifier, entity_extractor, geolocator, summarizer
writersturn whatever annotations are present into prose, and ignore the ones that are not — writer, summary_writer
filterstwo outboxes, keep and discard — relevance_filter, evaluator
the Python roleyour own function, no model involved
structuralsynchronizer, gate, select, router, record, deduplicator — they move messages rather than change them

The families matter because they tell you the shape of the wiring before you write any. An annotator has one outbox, so it can only ever be a link in a chain. A filter has two, and the second one is the one people forget.

Do this Wire a relevance_filter into an office and leave its discard outbox unconnected. Then run dsl draw. It lists every edge port to port, and puts everything connected to nothing in a block of its own: 
Screen   keep        ──▶  in_  Write

Not connected:
  Screen's discard  ──▶  nothing
That block is your list of gaps, in the form you can act on. While you are tuning a filter, wire its rejects to a readable sink instead of discard — you cannot tune what you cannot see.

2. Cost is an architectural choice

An office does not have to use one model. Each agent can name its own, and this is the whole of the syntax: 

Eve is an entity_extractor.
Eve's AI is ollama.          # local, free — fine for extraction
Riley is a writer.
Riley's AI is claude.        # the one place quality shows

Those two lines are the difference between a uniformly expensive office and a tiered one. The backends are anthropic (alias claude), openai (alias gpt), gemini, openrouter and ollama, and each has _creative and _precise variants — which are temperature 1.0 and temperature 0.1, nothing more mysterious than that. Only English roles use a backend at all; a Python role ignores the line.

The interesting question is not which model is best. It is how small a model each role can get away with, and the roles differ enormously. Pulling organisation names out of a news item is a job a 7B model does well. Writing the final briefing that a person will actually read is not. An office that sends both to the same frontier model is paying a writer's rate for an extractor's work, on every item, for ever.

openrouter exists in DisSysLab to let you find that line. One key reaches dozens of models — Qwen, Llama, Mistral, DeepSeek, and the closed ones too — so you can swap a role's model without installing another SDK. Its default is qwen/qwen-2.5-7b-instruct, and you override it per experiment with the OPENROUTER_MODEL environment variable. When you have found a small model that holds up, run it locally under ollama with the same model name: same prompts, same model, different inference path, no per-token cost.

Do this Take an office of yours that works, and push every annotator down to a small model while leaving the writer where it is. Run it on the same input twice and read both outputs side by side. Then push the writer down too, and read that. Where does it stop being acceptable? That boundary is a real engineering result about your office, and it is two lines of office.md to find.

3. Loops, gates, and why stopping is hard

A DisSysLab network may contain cycles, and that is a feature rather than an oversight. It is also the reason an end-of-stream marker is not enough and real termination detection is needed: in a loop there is no last message.

A loop should contain a gate, and the gate is what decides when to stop. The debate office in the gallery loops three panellists through a moderator and back until they agree, gated by the moderator. dsl check reports W7 for a feedback loop and tells you whether anything gates it.

Do this Run the debate office. Then take the gate out and run it again. Then put it back. Nothing in this course motivates the next two classes better than watching a correct-looking office refuse to finish.

4. dsl check is a safety tool, not a linter

Every finding dsl check makes carries a code, and the codes split into two kinds. A problem means the office is wrong — W1, an inbox nothing writes to, is the usual reason an office hangs. A note means read it and decide: the office is not wrong and the check still passes. You do not need to memorise any of them, because dsl checks W11 tells you what one means and dsl checks lists them all.

Two of the notes are the ones worth your attention, because they are about what your office can do rather than whether it runs:

codewhat it is telling you
W11text from the open web is reaching something that acts
W12a role's own Python is reaching outside the office

Neither is a bug. Both are the shape of an office that can be talked into doing something by whatever it just read. Knowing which of your agents sit on that path is the difference between a system you can reason about and one you are hoping about.

Do this Run dsl check on your own office and read every note, not just the problems. For each one, say in a sentence what the worst thing that could come through that path is. Keep the sentences. They are the beginning of a threat model, and you will want them later in the course.

5. Sources and sinks are the surface area

The install ships 46 sources and 26 sinks, and the point of knowing the range is that where a message comes from and where the answer goes are independent of everything in between. The same five agents can watch a news feed or a microphone, and can end in a file or in your inbox.

groupexamples
news and feedsbbc_world, hacker_news, rss (any feed), bluesky
researcharxiv_cs_ai, arxiv_cs_lg, and three more
markets, weatherstocks, kalshi, weather
sensorsaudio_mic, image_folder, audio_clip
personalgmail, calendar
plumbingwebhook (listens for POSTs), starter (one message to kick off a loop), mcp_source
sinks that actslack_sink, gmail_sink, webhook_sink, mcp_sink
sinks that recordjsonl_recorder, markdown_digest, report_html, console_printer

Note which of those are effectors — Slack, Gmail, a webhook, an MCP tool. Everything else computes; those four reach the world. That is also exactly the list W11 is worried about.

Do this Take one working office and change only its sink, three times: console_printer, then markdown_digest, then one that acts. Nothing else in the file should need to change. If it does, that tells you something about how your agents are coupled.

6. An office can be a component of an office

Two lines of grammar make composition possible. The first is the sub-office: 

news_monitor is an office at ../news_monitor.

The office at that path becomes one agent in this one. Build something small that works, then use it twice.

The second is for an office you have not finished: 

Jay is unassigned.

An office holding one of those is a draft, and that changes what the report means rather than what it says — the gaps are listed as still to do and dsl check exits 0. dsl run will refuse it, naming the agents whose job is undecided. Write down the names you know and leave the rest undecided; an unfinished office is not a broken one.

Do this Split an office you have already built into two, so that the inner one would be useful on its own, and wire it in with office at. Then run dsl draw on the outer one and see what it shows you about the inner.

7. Watch your own system run

The last one is the bridge to the next two classes. DisSysLab will hand you its own records of an execution, and they are exactly the objects the theory is about. 

dsl run  --trace              # one JSONL file per agent
dsl explain-trace             # merge them into one ordered sequence

dsl run  --snapshot-interval 5 # take a global snapshot every 5 steps
dsl show-checkpoint            # read one back as JSON

dsl run  --processes          # one OS process per agent, real parallelism

--trace writes one file per agent, each holding only what that agent did. That is not a convenience of the implementation; it is the only thing an agent can honestly record, and reconstructing one system-wide order from those files is the subject of the next class. dsl explain-trace does the reconstruction for you, so you can check your own answer against it.

--snapshot-interval writes, for each checkpoint, a directory holding manifest.json, a pickled state per agent under agents/, and — the interesting part — a pickled list of in-flight messages per channel under channels/. Those files are a global snapshot of your office: agent states, and the messages that were in transit. Why such a thing can be taken at all, when no two agents share a clock, is the class after next.

Do this Run an office of yours with --snapshot-interval 5, then open one channels/ file and find a message that was in transit — sent by one agent and not yet taken by another. Keep the checkpoint. You will be asked what it means in two weeks' time.
