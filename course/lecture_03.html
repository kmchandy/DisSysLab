Timeline Diagrams

A timeline diagram is a pictorial representation of system behavior as it evolves over time. Time flows from left to right in the diagram. For each agent, the diagram has a horizontal line that shows the behavior of that agent over time. Every action at that agent is shown on that agent's line. We call the line for agent X the X-timeline. The diagram has a horizontal line for every inbox and every outbox too, drawn near the agent that owns it. An agent only ever touches its own boxes; nothing an agent does reaches another agent directly. The diagram below shows a timeline diagram with two agents X and Y.

A thin horizontal line depicts an agent waiting to receive a message. A thick horizontal line or bar shows an active agent, and the length of the bar represents the time the agent spends on that action. Bars come in two kinds.

An agent's leftmost bar is its initial action, labeled init. An initial action by an agent sends a message (possibly to itself), but does not get a message from an inbox. Initial actions are merely convenient ways of representing computations starting up at each agent.

Every later bar is an agent that has got a message from an inbox for which it was waiting, and the bar represents the agent processing that message. Such a bar is labeled with the inbox from which the agent got the message.

Message timelines

A message gets from one agent to another in three steps, and the diagram draws each of them. When agent X places a message on its outbox A at a time t, a vertical arrow at t runs from the X-timeline to the A-timeline. When that message is removed from A at a time t and reaches inbox V at a later time t', a slanted arrow runs from the A-timeline at t to the V-timeline at t'. When agent Y removes the message from V at a time t, a vertical arrow at t runs from the V-timeline to the Y-timeline. Placing and removing take no time, which is why those arrows are vertical; the slant of the middle arrow is the only place delay appears in the picture. Each arrow is labeled with the name of its message.

A message therefore sits in a box for a stretch of time you can see: in an outbox from when the agent placed it there until it is removed, and in an inbox from when it arrives until the agent takes it. Each segment of a box's timeline is labeled with the queue of messages in that box over that stretch, so an empty box reads [ ] and a box holding two reads [m2,m4].

The segments of an agent's timeline in which the agent is waiting are labeled with the inboxes for which the agent is waiting. After the initial action of agent Y it waits for a message from inbox U, and that line segment is labeled waiting on U. In the diagram the message m1 from agent X arrives in inbox V, but agent Y goes on waiting on U.

The state at time t

The same computation, and a vertical line at time t cutting it. Every crossing tells you one thing, and the crossings together are the state of the system at t. Where the line crosses an agent line it gives that agent's state. Where it crosses a box line it gives the queue of messages in that box. Where it crosses a slanted arrow it has found a message that has left an outbox and not yet reached an inbox — a message in a channel.

Drawing the boxes is what makes this work. A message waiting in an inbox is not hidden inside the agent that owns the inbox; it is on a line of its own, and the cut crosses it like anything else. So there is nothing in the system the vertical line cannot see.

From the timeline to the dataflow graph

Prose to come. Name the five actions: X's initial action is 0 and Y's is 1; X's two R actions are 2 and 3; Y's U action is 4. Press Derive: the box lines go, each bar shrinks to a dot, and each message's three arrows collapse into one edge from the action that sent it to the action that received it. What is left is a dataflow graph. The actions are the nodes, and data travels along the edges: a message edge carries the message, and a horizontal edge carries the sending agent's own state from one of its actions to the next.

Paths in the dataflow graph

Prose to come. The same five events and the same edges. The question this figure answers is whether data from one event can reach another, and the answer is always the same kind of thing: is there a path? Data flows from 0 to 4 — not along any single edge, but by the path 0→2→4: x₁ carries X's state into action 2, and m3 carries the result on to action 4. Events 3 and 4 have no path between them in either direction, so no data travels either way and they are independent.

Moving events in time

Prose to come. Five events, named 0 to 4. Events 3 and 4 happen at different agents and neither depends on the other — they are the independent pair the last figure found. Slide them: 3 to the right, 4 to the left, until they change places. Each agent's own sequence of actions never changes, only where those actions sit in time. As long as no message is taken out of a box before it arrives, what you are looking at is another computation of the same system.

What each agent can record

Prose to come. During an execution every agent keeps its own history. For each of its actions it records three things: its state before the action, the message it received, and the messages it sent. Nothing else is available to it.

That history is a picture you already have. Take the timeline diagram and cover up everything except the agent lines and the short vertical arrows — the ones that put a message into an outbox and pull one out of an inbox. What is left is exactly what the two agents between them can write down.

Putting the records back together

Prose to come. Now try to reconstruct the timeline diagram from the two records alone. Assume every message carries a unique id, so a send record and a receive record that name the same id must be the same message. Connect each send to its matching receive. Each agent's own record already puts its own actions in order. Join both kinds of connection and ask what you are looking at.

It is the dataflow graph. Not the timeline diagram — the times are gone and no amount of matching brings them back — but the graph, exactly.

Many timelines, one graph

Prose to come. The records give us the dataflow graph and nothing more, and the reason is clocks. Each agent times its own actions by its own clock, and those clocks can drift apart by any amount whatever. So a time written in X's record and a time written in Y's record cannot be compared, and no arrangement of the two records recovers when anything happened relative to anything at the other agent.

Turn the question around. Which timeline diagrams would have produced this graph? We already know each agent's own sequence of actions. Place those actions anywhere in time you like, subject to one restriction: every message is sent before it is received. Every placement that obeys it is a timeline of the same system, and there are a great many of them.

What data reaches what

An event is an action by an agent. This computation has six of them, numbered 0 to 5. The numbers are names; they do not say which happened first, and events 0 and 1 happen at the same time.

Ask of any two events: could news of the first have reached the second? There are only two ways news travels. An agent remembers what it did, so news passes from each of its events to the next. And a message carries news from the event that sent it to the event that received it. Draw those two kinds of arrow and the question becomes a question about the picture: data flows from e to e′ — written e → e′ — when you can get from e to e′ by following arrows.

A message that changes nothing

The same six events, and almost the same messages. One thing is different. In event 2, agent X sends a message to Y as before — but into inbox W, and Y never waits on W. The message arrives on time, between events 3 and 4. It is simply never taken out.

So no event of Y is an event that received it, and the arrow it would have contributed to the dataflow graph does not exist. Click event 2: in the previous figure its data reached 4. Here it does not. The message crossed from one agent to the other and arrived before event 4 in time — and carried its data nowhere at all.
