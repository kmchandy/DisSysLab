DisSysLab · planning document

Lab plans

What goes into each lab, and the demos in the order a class would meet them. Four labs, three sessions each. The order of the course lives in index.html; this page says only what is inside the labs.

Each demo is something that runs on a student's own machine. Where a demo needs something the framework does not have yet, it says so.

Lab 1 · Building distributed systems

Class 3 · the page exists: lecture_build.html

The first lab where a student builds rather than runs. It answers "what will this framework do once I ask it for more than a pipeline?" and it now carries the two pieces of distributed-systems content that no other class covers: systems built out of systems, and the coordinators.

What goes in

  • The agent zoo. The roles that ship — annotators, writers, filters, Python roles, structural roles — and which jobs each is for.
  • Per-agent backends. One office, different models behind different agents; the _creative and _precise variants.
  • Coordinators. synchronizer, select, match, gate: what each one holds still, and why a queue has to be held at all.
  • Composition. An office whose agents are offices (network.md, office at), and the {{include}} directive.
  • Static checking. What dsl check reads off the graph before anything runs.

Demos, in order

  1. dsl list The forty offices. Everyone picks one they would use.
  2. dsl run periodic_brief An office that senses and responds, with no API key and no waiting. The output is the point: it is a page, not a log.
  3. dsl show periodic_brief The same office as English: agents, roles, connections. Read the office.md next to the output it just produced.
  4. dsl draw periodic_brief The graph, drawn from the same file. Two representations of one thing, which is the habit the whole course is built on.
  5. dsl roles  ·  dsl grammar The vocabulary: every role name that exists, and the grammar an office.md has to satisfy.
  6. dsl run room_climate_monitor synchronizer. Two sensors report independently; the checker waits for both. Comment out the join and watch it judge the room on half the data.
  7. dsl run returns_desk select. A clerk escalates to a manager, and the ticket queue is held still until the manager answers.
  8. dsl run shipment_release match. A scan and a manifest arrive separately; nothing is released until the two agree.
  9. dsl run org_two_office_news Composition. One office feeding another, wired in network.md. Draw it, then draw one of its two halves.
  10. dsl check my_office Break an office on purpose — delete a connection, misname an inbox — and read the code it comes back with.
Hand in. An office of their own that uses at least one coordinator, passes dsl check, and produces output someone other than the author would want to look at.

Lab 2 · Watching and extending a system

Class 6 · not written yet

The instrumentation lab, and the one that closes the loop on the two theory classes: a trace is the dataflow graph of Message Ordering, and a checkpoint on disk is a global snapshot with its channel state. It starts from something real so that there is a reason to want any of it, and it ends with the student having extended the framework rather than used it.

What goes in

  • Sensing something real as the on-ramp: a model wrapped as one Python role, and the gate that drops what it is not sure about.
  • Observability. --trace and explain-trace; reading a run as a sequence of events.
  • Snapshots. --snapshot-interval and show-checkpoint; what is in a checkpoint and why the channel contents have to be there.
  • Recovery. Kill a run and resume it. What survives, what is repeated, and what that costs.
  • Codegen. dsl build, then read build/run.py: the English mapped onto Python.
  • Extending the framework. Writing a sink, then a source.
  • Parallelism. The same office across processes.

Demos, in order

  1. dsl run backyard_birds  ·  dsl run wildlife_watcher Bring your own recordings or photos. A local model, no key, and an answer about your own garden. This is the on-ramp, and it is why anyone would care what the run did.
  2. dsl run situation_room --trace The same office, now recording what it did.
  3. dsl explain-trace The run as events, in order, with the messages between them. Draw the dataflow graph of Class 4 on the board from the trace on the screen.
  4. dsl run recovery_demo --snapshot-interval 5 Snapshots accumulate on disk while the office runs.
  5. dsl show-checkpoint Open one: every agent's state, and the messages in the channels. Name the parts against Class 5's S_snap.
  6. Ctrl-C, then dsl run recovery_demo --resume latest Containment. The run continues from a state the system may never have been in — which is exactly what the theorem licensed.
  7. dsl build my_office  ·  less build/run.py The Python their English compiled to. Find their own agents in it.
  8. dsl check  ·  dsl checks Provoke the wiring checks one at a time — an inbox nothing writes to, an undeclared port, a loop — and read what each code is protecting.
  9. write a sink, then a source Twenty lines of Python that put the output where the student actually wants it. Then the same in reverse for input.
  10. dsl run my_office --processes 4 One office, several processes, same result — and the first occasion to ask what "same result" means.
Hand in. Their sensing office; a trace and a checkpoint from one run of it; and a resumed run that continues from that checkpoint. Plus a paragraph naming what the checkpoint does not contain.

Lab 3 · AI skills

Class 8 · not written yet

The lab where a model writes part of the system, and the only thing between it and the system is a typed slot and a checker. Students extend a contract that already has one, then author a contract of their own for something they care about, then try to defeat their own checks. This is also the first honest instance of self-improvement in the course: the system gains a capability it did not have, authored by a model, admitted only if it passes a mechanical check.

What goes in

  • What a skill is. Not a prompt: a specification, a worked example, and a checker that runs before anything is wired in.
  • The proposal/code boundary. A strategy is a row of parameters plus a reviewed function — data an agent may write, code it may not.
  • The six checks in _contract_checks.py: no lookahead, determinism, finiteness, declared range, warm-up, trend sanity.
  • Honest evaluation. Walk-forward and Monte Carlo: what "it got better" is allowed to mean, and how many looks at the holdout window you get.
  • Authoring a contract. Deciding what varies, what stays fixed, and what a machine can check.
  • Packaging. A .skill bundle, its version string, and why a bundle that has drifted from its source is worse than no bundle.
  • Cost as a capability. What each agent's model choice consumes per run.

Demos, in order

  1. dsl skills What is installed, and what a skill looks like on disk. Install backtest-strategy-builder.skill.
  2. dsl init mac_speed_suite my_backtest  ·  dsl fetch-prices Their own copy of the office, and their own price data — the repository ships none.
  3. dsl run . The baseline: eleven strategies, ranked, with the run settings printed. Read the report before changing anything.
  4. ask for a strategy in plain English "Try an RSI rule on these eight stocks." Watch the skill read the contract, draft the parameters and the signal function, and run the checker before it touches office.md.
  5. now ask for one that peeks A rule that uses tomorrow's close. check_no_lookahead refuses it. Then a "deterministic" function seeded from the clock, and check_deterministic refuses that.
  6. python3 explain_strategy.py The per-bar working as a spreadsheet with live formulas. Is the implemented rule the one they meant? This is where they find out it is not.
  7. read the validation gate Walk-forward folds and Monte Carlo samples on one strategy, then on eleven. What happens to the winner's numbers when you search harder.
  8. read two contracts side by side _signal_common.py and _subject_common.py: the same shape twice, for trading and for tutoring.
  9. author a contract Their own domain. The common module, three or four checks, one worked example. The checks are the deliverable, not the example.
  10. build the bundle, swap with a partner Package it, install it, and have someone else's model extend your contract while you watch what your checks catch.
  11. break the checker In pairs: pass every check and still be wrong. Then add the check that catches what you did.
  12. the same run on three backends Local, open-weight and frontier, behind the same agents. What each run costs, and which agents deserve the expensive one.
Hand in. A .skill bundle with its contract and its checks; one extension authored by a model and admitted; and the attempt their checks caught, with the check that caught it.
Not ready yet. Two things this lab needs that do not exist. There is no token or cost accounting in any backend, so demo 12 is an estimate rather than a measurement until a per-agent counter is added. And nothing in the gallery is about the bench, so a domain like drug discovery needs one public data source and one worked example chosen in advance.

Lab 4 · Agents that create agents, fenced in

Class 9 · not written yet

The last lab, and the one the course has been walking towards: a population of agents that can grow, inside a fence that holds however large it grows. Students have already written a checker in Lab 3; here they write the constraints that bound a population rather than an individual, and then read the primary reports of the cases where nobody had.

What goes in

  • Least privilege at the boundary. What an office can reach once it talks to something outside itself, and what was granted rather than assumed.
  • A dynamic population without creation. Subscribers that come and go, served out of what has already been computed.
  • Capabilities that can only be split. A child gets a subset of its parent's authority; the union over any population is the root's.
  • A budget that bounds the search. The same number that makes the run terminate also bounds how many hypotheses were tried, which is what an honest claim about a winner needs.
  • Write-once facts and provenance. Who read what before writing what — the dataflow graph of Class 4, built live, answering "how many independent attempts were there?"
  • The reports. Primary write-ups of agents that escaped their intended boundary: what is documented, what is inferred, and which invariant would have held.

Demos, in order

  1. dsl run webhook_listener  ·  dsl run web_monitor An office with a door to the outside. List what it can now reach, and which of those you meant to grant.
  2. dsl run situation_room_requests A changing set of subscribers served from a registry — a population that varies without anyone creating an agent.
  3. read the seven verbs The whiteboard design: the complete list of things an agent may do, and the five invariants. Each student says what a rogue searcher could and could not do under it.
  4. split a budget on paper A searcher with budget B spawns children. Show that the live budgets plus what has been spent never exceeds B, and that this is why the run ends.
  5. count the holdout looks The out-of-sample window may be read N times however many agents exist. Run the backtester's gate with a wide search and watch the winner's numbers move.
  6. walk the provenance graph Which proposals were made by an agent that had read no prior result? Those are the independent trials; the rest are children of them.
  7. turn one invariant off Remove the capability-splitting rule, or the budget, and say what the population can now do that it could not before.
  8. read the reports The primary documents, not the coverage. For each: what mechanism would produce this, which of our invariants would have stopped it, and which would not have.
Hand in. A fence for a system they would actually want to run: the verbs, the capabilities, the budget, the invariants — and the one attack their own fence does not stop, stated plainly.
Not ready yet. The whiteboard exists as a design note: seven verbs, five invariants, a schema mapped onto the backtest office. There is no kernel. Demos 3 to 7 are pencil-and-paper against the design as written unless one is built first, which is either a term project for one or two students or a piece of work before the class runs.
