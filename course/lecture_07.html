Serializing Transactions

The FLP theorem says that distributed consensus is impossible in a system where messages are arbitrarily slow and an agent may halt. Let's look at the specification of the consensus problem again.

The distributed consensus problem: Each agent in a system proposes a value; the problem is to develop an algorithm by which all agents agree on a single value chosen among the proposed values. The algorithm has the following requirements:

  1. Validity: The value that the agents agree on must be a value proposed by at least one of the agents.
  2. Agreement: All agents must agree on the same value.
  3. Termination: Every agent must eventually decide: it computes a consensus value, and never changes it afterwards.

Why is this computation not serializable? Equivalently, why is there no consistent cut that separates red from blue steps?

That’s because any consistent cut in which past includes all blue steps must also include a red step. And similarly any consistent cut in which past includes all red steps must also include a blue step.

Condition 1. Serializable agent computations

For each agent, all steps of each transaction occur consecutively. blue, blue, blue… | red, red, …

Condition 1 says that for each agent’s computation (remember that an agent’s computation is its log of steps at the agent) can be partitioned into sequences of steps where each partition consists of the steps of exactly one transaction and all the steps of that transaction. This diagram shows 5 agent computations, and for each computation all steps of one transaction (blue) occur before all steps of a different transaction (red).

Condition 2. The order of transactions

Condition 2: The order of transactions is the same for all agent computations. If blue before red in the computation of one agent, then blue before red in the computation of all agents.

Condition 3. Messages stay inside a transaction

Condition 3: All messages in a transaction are sent and received by steps in the transaction. All blue messages are between blue steps; all red messages are between red steps.

Observation If conditions 1, 2, 3 are satisfied in a data flow graph then the graph can be partitioned by consistent cuts (past_0, future_0), (past_1, future_1), (past_2, future_2), … where past_(i+1) consists of past_i and all the steps of exactly one transaction.

The diagram shows only two transactions, but you get the idea. past_0 is the empty set. past_1 consists only of blue steps and all the blue steps. past_2 consists of past_1 and only red steps and all the red steps,…

Theorem

A sufficient condition for serializability of transactions is as follows.

  1. Associated with each transaction is a unique id where transaction ids are totally ordered.
  2. For each agent: all steps of a transaction with id T occur after all steps of a transaction with id T’ if T’ < T
  3. All messages sent in a step of a transaction with id T are received in a step of the same transaction.

Conditions 1, 2, and 3 are satisfied by the requirements of the theorem.

Steps of each agent’s computation occur in order of increasing transaction id. For agent U: all steps of the green transaction occur before all steps of the blue transaction which occur before all steps of the red transaction. Similarly for agent V.

How can we make transactions serializable?

Transaction ordering, green -> blue -> red What should happen when a message arrives from an earlier transaction?

Message from green transaction arrives when agent U has moved forward to the blue transaction?

We require that all messages sent in green steps are received in green steps. What to do?

Rule 1 Ignore the transaction — treat it as lost.

So, no messages from earlier transactions are received in later transactions.

Transaction ordering, green -> blue -> red What should happen when a message arrives from a later transaction?

Message from red transaction arrives when agent U is at earlier transaction?

We require that all messages sent in red steps are received in red steps. What to do?

Rule 2 When an agent receives a step from a later transaction the agent starts executing the later transaction.

These two rules guarantee that a message sent in a step of a transaction with id t is received in a step of a transaction with id t (or is lost).

Transaction ids or Epochs

Transaction ids or Epochs Similar to (but not same as) logical time · Transaction id: (number, agent id)

This diagram shows the computation of a single agent. Associated with each edge and each step is a transaction id or epoch.

Transaction ids or epochs are similar to but not identical to logical times. Consecutive steps at an agent can have the same epoch whereas a later step at an agent has a larger logical time.

Epochs are unique by making each epoch a pair: a number and an agent id. Assume agent ids are a total order and use agent ids to break ties. For example (10, A) < (10, B).
