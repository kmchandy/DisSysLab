Serializability of Transactions

The last class ended badly: in an asynchronous system where one agent may halt, no algorithm can promise to reach consensus. This class and the next build one that gets as close as the theorem allows, and this class is the half that has nothing to do with consensus at all.

The reason for spending a class on it is the proof. An algorithm that runs over a network where messages are lost, duplicated and delivered out of order, and where agents halt and come back, is a nightmare to reason about directly. Serializability converts that nightmare into a proof about a nondeterministic sequential program — a for loop — and the conversion is what the next class stands on.

The system we are heading for

Two layers of agents, and only two. Proposers are called clients and acceptors are called servers. Each client sends messages to, and receives messages from, servers. Servers do not communicate with each other, and clients do not communicate with each other. We know an upper bound N on the number of servers, and some of the servers may have halted permanently. Assume at least one server has not.

What serializable means

Colour the steps and messages of a computation by which transaction they belong to. Here two transactions, blue and red, run across four agents, and their steps are interspersed: some red steps occur before some blue steps and some blue steps occur before some red ones. A dotted line is a message that was sent and lost.

Press Permute. The steps slide into a new order in which all the blue steps come before all the red ones — and nothing about the computation has changed. Check it: the log of each agent is the same in both, step for step, and every message is still received after it was sent. What the permuted picture shows is a computation in which while the blue transaction is executing no other transaction is executing, and likewise for red. That is what serial means, and a computation that can be permuted into a serial one is serializable.

When it cannot be done

Not every computation can be permuted into a serial one, and the two ways it fails are worth seeing, because the conditions that follow are exactly the conditions that rule them out. Remember what a cut may and may not be: to put a step in the past you must put everything before it on that agent in the past as well.

Three conditions

Condition 1. Serializable agent computations. For each agent, all steps of each transaction occur consecutively: blue, blue, blue… then red, red… An agent's computation is its log of steps, and that log can be cut into blocks, each block holding all the steps of exactly one transaction.

Condition 2. The order of the transactions is the same for all agent computations. If blue comes before red in the computation of one agent, then blue comes before red in the computation of every agent.

Condition 3. All messages in a transaction are sent and received by steps in that transaction: all blue messages are between blue steps, all red messages between red steps.

Observation If conditions 1, 2 and 3 hold in a dataflow graph, then the graph can be partitioned by consistent cuts (past0, future0), (past1, future1), … where pasti+1 is pasti together with all the steps of exactly one transaction.

A sufficient condition

Theorem Transactions are serializable if: 1. associated with each transaction is a unique id, and transaction ids are totally ordered; 2. for each agent, all steps of a transaction with id T occur after all steps of a transaction with id T′ whenever T′ < T; and 3. all messages sent in a step of a transaction with id T are received in a step of the same transaction.

Conditions 1, 2 and 3 of the previous section are satisfied by these requirements, so the observation applies and the computation comes apart into transactions. Here are two agents that meet them, with three transactions whose ids are the colours green < blue < red.

How to make it happen

The theorem tells us what we need. It does not tell us how an agent, which can see only its own state and its incoming messages, is supposed to arrange it. Two questions, and their answers are the whole mechanism.

Where the ids come from

One thing is still missing: the ids themselves. Each transaction needs an id, the ids must be totally ordered, and no two transactions may share one. Call them epochs. An epoch is a pair — a number and an agent id — and agent ids break ties, so (10, A) < (10, B). Two agents may pick the same number and still get different epochs.

That is serializability: three conditions, a theorem that implies them, two rules an agent can actually follow, and epochs to number the transactions with. Nothing in it mentions consensus. What it buys is the right to stop thinking about a network that loses and duplicates and reorders messages, and to think instead about transactions that happen one after another — which is where the next class begins.
