The Paxos Algorithm

The Paxos algorithm is a distributed consensus algorithm created by Leslie Lamport. The FLP theorem says no distributed consensus algorithm can guarantee validity, agreement and termination if a single agent may halt. Paxos guarantees validity and agreement, but not termination.

Specification

A set of agents called proposers propose values for a consensus. A set of agents called learners determine the consensus value. Associated with each proposer p is a constant p.VALUE, and each learner L has a local variable L.value.

  • All learners only learn values that were proposed.
    For all learners L:
    (L.value = null) OR (exists proposer p where: L.value = p.VALUE).
  • All learners learn the same value.
    For all learners L, L′:
    (L.value = null) OR (L′.value = null) OR (L.value = L′.value).
  • A learner does not change what it learned.
    For all learners L:
    L.value changes (from null to a non-null) at most once.

The algorithm

The previous class described a model of transactions in a computation and gave sufficient conditions for transactions to be serializable. Serializability allows us to convert a system in which messages may be lost, duplicated and delivered out of order, and in which agents may halt, into a sequential program.

Proposers and acceptors

We describe the Paxos algorithm in two parts. The first part deals with network of two layers of agents: proposers that propose values to be considered for consensus, and acceptors that receive proposals and carry out computations that lead to a consensus.

Proposers send messages to, and receive messages from, acceptors. Acceptors send messages and receive messages from proposers. Proposers do not communicate directly with each other. Likewise acceptors do not communicate directly with each other. In our model each proposer and each acceptor has a single outbox and a single inbox. (Later we will add a second outbox for acceptors, but that outbox plays no part in the first part of the algorithm.)

Associated with each proposer p is a local constant p.VALUE which is the value that p proposes as a candidate for consensus. Each acceptor q has a local variable q.v where q.v has components q.v.s and q.v.t, and q.v.s is a candidate consensus value and q.v.t is the id of the transaction in which q.v.s was assigned its current value. Let N be the number of acceptors, and let M acceptors be a majority. M = floor(N/2) + 1.

An outline of the algorithm

The algorithm executes transactions in increasing order of transaction id. A transaction consists of the following steps in which T, p, R, and W are determined nondeterministically.

  1. Select transaction id and proposer: Select a transaction id T that is larger than the ids of all previous transactions. Select a proposer p that starts executing a new transaction with id T.
  2. Proposer reads acceptor variables: p reads the local variable r.v of acceptor r in a set R of acceptors.
  3. Proposer writes acceptor variables: If the size of R is at least M, p computes a value d from the values of acceptor local variables, r.v, that p read in this transaction. p assigns d to local variable, q.v, of acceptor q, for all q in a set W of acceptors.

The transaction T, p, R and W are selected nondeterministically. 

if len(R) >= M:
    d = f(p, r.v for r in R)
    for q in W:
        q.v.s, q.v.t = d, T
def f(p, list_of_rv):
    if all(rv.s == null for rv in list_of_rv):
        # no acceptor holds a candidate: propose p's own value
        return p.VALUE
    else:
        # return the candidate value that was assigned most recently among
        # the acceptors that were read: the rv.s with the largest rv.t
        t_max = max(rv.t for rv in list_of_rv)
        r_s_list = [rv.s for rv in list_of_rv if rv.t == t_max]
        return r_s_list[0]

Properties of the algorithm

Acceptors only accept values proposed by proposers:
For all acceptors q: (q.v.s = null) OR (exists proposer p: q.v.s = p.VALUE)

Monotone nondecreasing acceptor timestamps
If in a transaction q.v.t = t* then in all subsequent transactions : q.v.t >= t*.

Theorem: Candidate value assigned to a majority in a transaction remains unchanged

If the set W of acceptors assigned values in a transaction with id t* is a majority, and s* is the candidate value assigned in the transaction, then
for all q: (q.v.s = s*) OR (q.v.t < t*).

Proof by induction Base case — The condition holds for the transaction with id t where t = t*.

Induction step: Assume that the conditions holds for a transaction with id t >= t* and show that it holds for the next transaction with id t' > t.

If len(R) < M then acceptor values are not modified in the transaction with id t', and so the condition continues to hold.

If len(R) >= M then there is at least one element common to R and W*, because two majorities must have an element in common. Let q be an acceptor in R and in W*. Then q.v.t >= t*, because of monotone nondecreasing timestamps. So t_max >= q.v.t >= t*.

For all q: (q.v.s = s*) OR (q.v.t < t*). Therefore, if q.v.t = t_max then q.v.s = s*. And the value returned by function f is s*.

Learners

The acceptors know collectively when a majority of them reach a consensus. How can a learner know if a majority has reached consensus?

When an acceptor q changes its value it sends a message containing q.v to all learners. If a learner L has a null value and L receives messages from at least M acceptors, q, where all the messages have the same value of q.v, then L sets L.value = q.v.s. The proof of correctness is as follows.

Validity: An acceptor q assigns only proposer values to q.v.s, and so L.value is only assigned proposer values.

Agreement: After a majority W of acceptors is assigned a value s*, t*, all changes to q.v for any acceptor q assign q.v.s = s*. Therefore for t* < t', if another majority W' of acceptors is assigned s', t' then s' = s.

Determining consensus on sequences of proposals

The Paxos algorithm that we described enables learners to determine a single consensus value. In many problems, consensus has to be reached on a sequence of values. Determining a consensus on an account ledger illustrates the problem.

Consider the following sequence of deposits and withdrawals from an account which has $0 initially. Proposer 0 proposes "Deposit $100 in the account." Proposer 1 proposes "Withdraw $95", presumable expecting to wait until the deposit was made. So the sequence of operations on the consensus ledger could be

  1. Proposer 0's proposal is the consensus. Balance is $100
  2. Then: Proposal 1's proposal is the consensus. Balance is $5

A problem arises if the withdrawal is made before the deposit.

  1. Proposal 1's proposal is the consensus. Balance is -$95. Penalty $5
  2. Then: Proposer 0's proposal is the consensus. Balance is $0.
We want a consensus on the sequence of operations on the ledger.

The algorithm can be extended from determining consensus on a single value to a sequence of values as follows. Learners send sequences that they learn to proposers. A proposer's proposal extends the sequence that the proposer knows is in the consensus followed by a single additional proposed value. A proposer that reads q.v.s = sequence_0 and u.v.s = sequence_1 in the same transaction, treats q.v.s as null if the length of sequence_0 is less than that of sequence_1.

Acceptor q

# q.v is the pair (q.v.s, q.v.t): the candidate value q holds and the id
# of the transaction that assigned it. q.t is the id of the transaction
# that q is processing.
q.v.s, q.v.t = null, 0
q.t = 0

def receive(request, p):
    if request.t < q.t:
        # a request from an earlier transaction: treat it as lost
        return
    q.t = request.t
    if isinstance(request, ReadRequest):
        send(Reply(q.v, q.t), p)
    else:
        # a WriteRequest, which carries the value and the transaction id
        q.v.s, q.v.t = request.s, request.t

Proposer p

# p.t is the id of the transaction p is executing, and p.replies holds the
# replies it has received in that transaction, one for each acceptor.
p.t = 0
p.replies = {}

def receive(message, sender):
    if isinstance(message, ClockTick):
        # start a new transaction with an id larger than any p has used
        p.t = next_id(p.t)
        p.replies = {}
        for q in acceptors:
            send(ReadRequest(p.t), q)
    elif isinstance(message, Reply):
        if message.t == p.t:
            # replies from other transactions are ignored
            p.replies[sender] = message.v
            if len(p.replies) == M:
                # the M-th reply completes the read set R
                d = f(p, list(p.replies.values()))
                for q in acceptors:
                    send(WriteRequest(d, p.t), q)
