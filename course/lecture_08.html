The Paxos Algorithm

Last class was about serializability, and had nothing to do with consensus. This class spends it. The rules on epochs from last class turn a system in which messages are lost, duplicated and delivered out of order, and in which agents halt, into a nondeterministic sequential program — a for loop — and the algorithm we are about to write is short enough to fit on one slide. Its correctness is not obvious, which is the point of the proof at the end.

The algorithm is Leslie Lamport’s. The FLP theorem says no algorithm can promise to reach consensus in a system like this, so Paxos does not promise it. It promises that the agents never disagree, and it reaches a consensus whenever the network gives it enough of a quiet spell to do so.

Proposers, acceptors, learners

In the Paxos algorithm there are three layers of agents. Proposers propose values. Acceptors receive proposals from proposers and change their local variables. Learners receive messages from acceptors, and it is the learners that come to a consensus about the values the proposers proposed.

Each learner L has a local variable L.value, and each proposer P has a local constant P.VALUE. The specification is about proposers and learners only; acceptors exist to implement it.

  • Learners only learn values that were proposed. For all learners L: L.value = null or there is a proposer p with L.value = p.VALUE.
  • All learners learn the same value. For all learners L, L′: L.value = null or L′.value = null or L.value = L′.value.
  • A learner does not change what it learned. If it learns x at any point then it has learned x from that point on: for all learners L and all non-null x, stable(L.value = x).

Proposers send messages to, and receive messages from, acceptors. Proposers do not talk to each other. Acceptors send messages to learners and never receive messages from them.

Clients and servers

Back to the problem of consensus with clients and servers. We know an upper bound N on the number of servers, and some of the servers may have halted permanently. Assume that at least one server has not halted permanently.

We restrict attention to transactions of one shape. A client sends read requests to servers. It receives replies from a set R of servers. If it receives replies from at least M servers it sends write requests to all servers, and those requests reach a set W of servers.

The transaction if len(R) >= M: for q in W: q.v = f_p(r.v for r in R)

The sets R and W are nondeterministic: the network decides them, not the algorithm. If R has fewer than M elements then W is empty — the transaction reads and writes nothing.

The rules that make it serial

Every request carries the epoch of the transaction that sent it, and every server q keeps the epoch q.t of the transaction it is processing. The three rules from last class are all that is needed.

  1. r.t < q.t. A request from an older transaction is discarded without being processed. A discarded request has the same effect as a request that was lost.
  2. r.t = q.t. A request from the transaction the server is already processing is answered.
  3. r.t > q.t. A request from a newer transaction makes the server stop processing the transaction with epoch q.t, raise q.t to r.t, and answer the request.

The server

A server gets read requests and write requests from clients. Requests sent in earlier epochs are ignored and treated as lost. A server q replies to a read request by sending its value q.v and the epoch q.t. When it gets a write request it assigns the requested value to q.v. 

# initialization
q.v, q.t = init, 0
start()

def receive(request, client):
    if request.t >= q.t:
        q.t = request.t
        if isinstance(request, ReadRequest):
            send(Reply(q.v, q.t), client)
        else:
            # a WriteRequest
            q.v = request.v

The client

A client receives two kinds of message: clock ticks and replies to read requests. A clock tick can be thought of as a physical clock. When a tick arrives the client starts a new transaction, identified by the epoch p.t — a number together with the client id, which is not written out here. Later transactions started by a client have larger epochs. p.copy is the dict the replies are collected in. 

# initialization
p.t = 0
start()

def receive(message, sender):
    if isinstance(message, ClockTick):
        p.t = p.t + pos()          # start a new transaction
        p.copy = {}
        for q in Q: send(ReadRequest(p.t), q)
    else:                          # a reply to a read request
        if message.t == p.t:       # ignore replies from other transactions
            p.copy[sender] = message.v
            if len(p.copy) >= M:
                v = f_p(list(p.copy.values()))
                for q in Q: send(WriteRequest(v, p.t), q)

The client ignores a reply that belongs to a different transaction. Once it holds M replies it computes a value with f_p and asks every server to write it, stamped with the epoch of the transaction.

What a server stores

Now extend the algorithm so that a server records when it assigned a value. A server variable q.v becomes a pair

Server value q.v = (q.v.s, q.v.t) — q.v.s is a candidate consensus value, and q.v.t is the epoch in which q last assigned it.

Note the two clocks a server keeps. q.t is the epoch of the transaction the server is currently processing; q.v.t is the epoch in which it last wrote its value. A read request bumps the first and leaves the second alone.

The sequential program

Serializability earns us the right to write the whole system as one nondeterministic sequential loop. Transaction i has epoch t[i], is executed by client p[i], reads the set R[i] and writes the set W[i]. 

for i in positive_integers:
    if len(R[i]) >= M:
        for q in W[i]:
            q.v.s, q.v.t = f_p[i](r.v for r in R[i]), t[i]

Three questions are left, and nothing else is:

  1. What should M be?
  2. What should f_p be?
  3. What is the consensus value?

M is a majority

If M is less than a majority then two concurrent transactions could read the values of two disjoint sets of servers, and neither would see what the other had done. If M is nearly all the servers then transactions may never get to the write stage at all. A majority is a reasonable place to start.

A consensus is a majority holding the same pair

A consensus is reached when some number of servers hold identical values. How many? If the number is large a consensus is less likely to be reached; if it is too small there could be two consensus values at the same time, which violates the definition of consensus. So, again, a majority.

Consensus If every server q in a majority has the same q.v — the same q.v.s and the same q.v.t — then q.v.s is the consensus value.

f_p takes the most recent candidate

If the client hears from a majority and every candidate it hears is null, nobody has written anything it could contradict, and the client proposes its own value. Otherwise it must not invent a value: it takes the candidate that was written most recently among the replies it holds. 

def f_p(self, list_of_rv):
    if all(rv.s == null for rv in list_of_rv):
        # nobody has a candidate: propose this client's own value
        return p.VALUE
    else:
        # t_max: the most recent epoch in which a server was updated
        t_max = max(rv.t for rv in list_of_rv)
        r_s_list = [rv.s for rv in list_of_rv if rv.t == t_max]
        return r_s_list[0]

Every element of r_s_list is the same value, because they were all written by the same transaction — the one with epoch t_max. So returning the first of them is returning the only one.

A scenario

Before the proof, one run of the algorithm, to be sure every step is clear. The scenario is not part of the proof. Five servers q0 … q4 and three clients c0, c1, c2 proposing green, blue and red. Initially every server has q.v = (null, 0) and q.t = 0. A majority is three.

Why it works

Suppose a majority of servers hold the same pair. The theorem says that from that moment on no server can ever hold a different value at that epoch or later — so the consensus cannot be undone.

Theorem If there is a majority W of servers with q.v = (s*, t*) for all q in W, then for every server u afterwards: u.v.s = s* or u.v.t < t*.

Say the majority was written on iteration i*, so W[i*] is a majority and t* = t[i*]. Because q.v.t never decreases, every server in W[i*] keeps q.v.t >= t* for ever after.

Assertion 1

For every iteration i > i* there is a majority of servers with q.v.t >= t*.

The invariant

For all servers q: if q.v.t >= t* then q.v.s = s*.

The invariant holds trivially at i*. Assume it holds at some iteration i >= i* and prove it for i+1. If W[i+1] is empty the invariant continues to hold. If it is not empty then R[i+1] is a majority, and any two majorities have an element in common, so by assertion 1 there is a server q in R[i+1] with q.v.t >= t*. Then t_max = max(q.v.t for q in R[i+1]) >= t*, and by the induction hypothesis the candidate written at t_max is s*. So f_p[i+1] returns s*, and every server it writes is written with s* at a larger epoch.

Take away

The algorithm is short, and that it is correct is not evident. Breaking the proof into two steps — serializability, and then consensus — is what makes it manageable. Serializability converts a proof about a complex message-passing system, in which messages are lost, duplicated and delivered out of order and agents halt, into a proof about a nondeterministic sequential program: a for loop.

What is left: we have only proved that a consensus, once reached, is never contradicted — the first step of the algorithm. The learners, and sequences of values rather than a single one, come next.
