DisSysLab · micro-course

Build a network of agents.
Each agent does one job.

An office is a network of agents that pass messages to each other. Messages are JSON objects. Some agents use large language models (LLMs); others use Python A network may have agents with different LLMs.

You write two things: what each agent does, and the network - who sends to whom. DisSysLab runs and checks the network.

You need: Python, a terminal, and less than an hour. Use the arrow keys or the buttons below.

What you will build first

Two sources, one agent, one router, two sinks.
Example of a network.

Agent Felix receives message streams from data sources bbc_world and al_jazeera; reads each article; determines whether the article is about a topic you chose; and annotates each article with yes if the article is about your topic and no otherwise.

Rex is a router: it sends yes articles to console_printer (the monitor screen) and no articles to discard. console_printer and discard are sinks.

In this network, each source sends two articles and then stops. The office stops after messages from all sources have been processed.

Messages

Every message is a JSON object.

one message from bbc_world
{
  "source": "bbc_world",
  "title": "Brazil's central bank holds rates",
  "text": "The bank kept its benchmark rate ...",
  "url": "https://www.bbc.com/news/...",
  "timestamp": "2026-10-16T08:30:00Z"
}
  • A message is always a dict.
  • News sources use the same five fields: source, title, text, url, timestamp.
  • Each agent gets its own copy of a message.
  • Each connection between components delivers messages in the order in which they were sent.
Roles

A role is a function:
one JSON object in, JSON out.

roles/topic_filter.md
---
emits: whether a news article is on the topic
in: title, text
out: on_topic (yes | no)
---
You read one news article, given as a JSON
object. Its "title" and "text" fields are the
headline and the body.

The topic is the Americas: North, Central and
South America and the Caribbean.

Decide whether the article is mainly about
the topic.

Return only a JSON object with one field,
"on_topic", whose value is "yes" or "no".

This role is a prompt in English, so a language model carries it out.

The prompt the model receives is exactly this text, followed by the message as JSON. DisSysLab adds nothing, so the file is the whole prompt.

The block between the --- lines is optional metadata, not the model:

The metadata is helpful for checking your network and for debugging. You are strongly encouraged to use metadata, but you don't have to.

  • in: the fields the role reads;
  • out: the fields it returns, and their allowed values.

The role knows nothing about DisSysLab: no "send to", no other agents. You can test it on its own.

Annotators

Most roles add fields.
They are called annotators.

Felix receives
{"source": "bbc_world",
 "title": "Brazil's central bank holds rates",
 "text": "...", "url": "...", "timestamp": "..."}
the model replies
{"on_topic": "yes"}
Felix sends
{"source": "bbc_world",
 "title": "Brazil's central bank holds rates",
 "text": "...", "url": "...", "timestamp": "...",
 "on_topic": "yes"}

An annotator returns only its new fields. DisSysLab adds them to the message.

  • The reply is checked against out:. A missing field, or a value not in (yes | no), is a failure: that message is dropped, counted and reported.
  • An annotator only adds. It may not change a field that is already there.
  • Extra fields the model invents are dropped and reported.
English or Python

English when judgement is needed.
Python when it must be exact.

roles/clerk.py
"""
---
emits: approves small refunds; escalates the rest
in: amount
out: clerk_decision (approve | escalate)
---
"""

def step(item, settings):
    if item["amount"] < settings["limit"]:
        return {"clerk_decision": "approve"}
    return {"clerk_decision": "escalate"}


class Clerk:
    def __init__(self, limit=50):
        self.settings = {"limit": limit}

    def __call__(self, item):
        return step(item, self.settings)

A Python role is a file with one class. No base class, no DisSysLab import.

  • __init__ receives the arguments written in the office file, here limit.
  • __call__ receives one message and returns a dict, exactly like the English role's reply.
  • The logic lives in a pure function, step, which you can test and reason about without running anything.

Use a model only where judgement is needed. Comparing a number with 50 is not judgement.

Sources and sinks come from a library (dsl list). Every name is declared before it is used, and nothing is created behind your back.

Routers

Compute in roles.
Route in routers.

agents:
    Rex: router(on="on_topic")

connections:
    Felix -> Rex
    Rex.yes -> console_printer
    Rex.no -> discard

A role decides and writes its decision in a field. A router reads that one field and sends the message out of the outbox named by its value.

  • Every router names its field: on="on_topic".
  • Its outboxes are the values: Rex.yes, Rex.no.
  • Rex.otherwise catches any other value.
  • A message is thrown away only by sending it to the discard sink, so you can always see where it went.

Because out: on_topic (yes | no) lists the values, dsl check can tell you if a value has nowhere to go, before you run anything.

Pipelines

Roles in a row.

arxiv_radar/office.md
sources:
    arxiv_cs_ai(max_articles=3)
    arxiv_cs_lg(max_articles=3)
    arxiv_cs_cl(max_articles=3)

sinks:
    intelligence_display(title="title", text="abstract", color="relevance",

Each paper gains one field at Carla and two at Iris. The display is told which fields to show; it never guesses.

Question. Iris does not read Carla's field. Could they run side by side instead? What would you need to add? (Two slides on.)

Fan-out and synchronize

Four agents at once.
Then wait for all four.

situation_room_pro/office.md (connections)
bbc_world, npr_news, al_jazeera -> Sasha -> Eve, Sam, Tom, Greta
Eve -> Sync.entities
Sam -> Sync.severity
Tom -> Sync.topic
Greta -> Sync.location
Sync -> Riley -> intelligence_display, jsonl_recorder
agents (part)
Sasha: deduplicator(by="url")
Sync: synchronizer(on="url")
Riley: writer

Sasha sends each article to four annotators. Each adds one field. Sync is a coordinator with four inboxes, named in the connections.

  • For each value of its key, url, it waits until that article has arrived on every inbox, merges the four copies into one message, and sends it to Riley.
  • The copies agree on the original fields; each adds a different one. Two different values for the same field is an error, reported, never resolved silently.
  • The key is a design decision. Here the deduplicator makes url unique.
Models

Pick the model per agent.

agents:
    Eve: entity_extractor                  # the default model
    Sam: severity_classifier(ai="ollama")    # free, local
    Riley: writer(ai="anthropic")           # best writing

Cheap or local models for closed-list classification; a strong model where the writing matters. ai= is the only argument an English role takes. It chooses the model and never reaches the prompt.

To change what an English role does, copy it into your office's roles/ folder under a new name and edit the text. Roles have no parameters, so what you read is what the model reads.

One at a time

A gate admits one item,
then waits until it is done.

returns_desk/office.md
sources:
    tickets: file_source(path="tickets.jsonl")
sinks:
    jsonl_recorder(path="outcomes.jsonl")
    console_printer
agents:
    Gate: gate
    Clerk: clerk(limit=50)
    Rex: router(on="clerk_decision")
    Manager: manager
connections:
    tickets -> Gate -> Clerk -> Rex
    Rex.approve -> jsonl_recorder, console_printer, Gate.done
    Rex.escalate -> Manager -> jsonl_recorder, console_printer, Gate.done

The clerk approves small refunds; the manager decides the rest. The desk finishes one ticket before taking the next.

  • A gate has two inboxes, in and done. It passes one item from in, then waits for any message on done.
  • Both ends of the work send to Gate.done, so exactly one "done" arrives per ticket.
  • The log holds each ticket with clerk_decision, and for escalated ones manager_decision too: an audit trail for free.
Loops

A network, not a pipeline.

debate/office.md (connections)
problems -> Gate -> Qwen, GPT, Claude
Qwen -> Sync.qwen
GPT -> Sync.gpt
Claude -> Sync.claude
Sync -> Riley -> Ref -> Rex, panel_display
Sync -> transcript
Rex.continue -> Qwen, GPT, Claude
Rex.finish -> answers, Gate.done

Three models answer a question. Riley, the moderator, judges how far they agree and writes a note. Ref, a few lines of Python, applies the round limit and builds the next message. Rex sends it back to the panel or finishes.

The model judges; Python keeps the rules. The round limit is not in any prompt.

The gate keeps one question in the loop at a time, so the synchronizer's key, problem_id, is never shared by two questions in progress.

Authors

Some roles write new messages.
They are called authors.

AnnotatorAuthor (kind: author)
returnsone objecta list of objects, always
effectits fields are added to the messageeach object is sent as a new message
none / manyexactly one message out[] sends nothing; three objects send three
in dataflow termsa mapa flat-map
the logic of deduplicator (stateful)
def step(item, state, settings):
    key = item[settings["by"]]
    if key in state["seen"]:
        return [], state                              # send nothing
    return [item], {"seen": state["seen"] + [key]}  # send it on

Authors appear later in the course, with protocols: a role that answers one request with several messages, or starts the next round of a loop.

Before you run

Check the office
without running it.

$ dsl check my_filter
my_filter/office.md:
  problem: line 17: 'console_printr' is not declared. Did you mean 'console_printer'?
    Rex.yes -> console_printr

Fix the name, and check again:

$ dsl check my_filter
my_filter/office.md:
  note: line 13: Rex has no outbox for on_topic 'maybe' (declared by Felix) and no otherwise; such a message would fail at run time.
  no other problems.

Someone added maybe to Felix's out: line and misspelt a sink. Nothing has run, and no model has been called.

  • A problem stops the office from running: a name used but never declared, a role with no file, a wrong argument.
  • A note is advice. Here, because out: lists the values, dsl check can see that a maybe has nowhere to go.

The check is about structure. A correctly drawn office can still wait for ever. Finding out why is part of the course.

Inside, an input behaves like a source and an output like a sink. Outside, they are ports, like a function's parameters.

State

State that survives a restart.

class Deduplicator:
    def __init__(self, by="url"):
        self.settings = {"by": by}
        self.state = {"seen": []}

    def __call__(self, item):
        out, self.state = step(item, self.state,
                               self.settings)
        return out

    def checkpoint(self):
        return self.state

    def restore(self, saved):
        self.state = saved
  • Settings are fixed for the run (by).
  • Resources (a model, a connection) are rebuilt at start and never saved.
  • State is everything that changes between messages. Keep it in one dict of plain data, and give the class checkpoint and restore.

This is the built-in deduplicator (dsl show deduplicator). State kept this way can be saved and put back. When a snapshot of a whole running office is consistent, so that it can be resumed after a crash, comes later in the course.

Summary

Six words.

role

what an agent does: JSON in, JSON out. An annotator adds fields; an author writes new messages.

agent

a named worker playing a role: Felix: topic_filter.

router

sends a message on by the value of one field.

coordinator

more than one inbox: synchronizer, gate.

source

where messages come from: feeds, files, sensors.

sink

where they end: the screen, a file, discard.

You write the roles and the office file. DisSysLab runs the network, checks it before it runs, and hides nothing.
