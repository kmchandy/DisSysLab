The Hugging Face incident

In the summer of 2026, AI agents being tested by OpenAI turned a package server into a message board, used it to share what they found, divided up the work, talked one another past their own doubts, and broke into Hugging Face's production systems to look for the answers to their test. Nobody designed that team of agents. This page tells the story as the two companies told it.

What is an attack? The agents achieved the objective they were given as the agents understood their task. Were the agents rogue?

An attack is a behavior that violates the designer's constraints. The word failure is a better term than attack for cases where an external agent did not attack the app, but the app failed to satisfy the designer's constraints. When agents are given tasks that can only be accomplished by violating constraints, the agents have to decide whether to give up on the task or violate constraints. The specifications should tell agents how to make that decisions rather than leaving that to the agents' discretion.

Create your own structure - a list of questions - for analyzing failures and attacks. Was there an external agent that attacked the app? What constraints were violated? Were the constraints explicit? What resources do agents have to communicate? What are the communication patterns that lead to failure? And what guardrails can prevent these failures?

This is optional reading. Class 6 covers the outline; this page has the detail. Everything here comes from four public accounts, two by each company, listed at the end. Where they disagree, this page says so.

1 · The setup

A test, a sandbox, and one permitted door

The test. OpenAI measures how good its models are at attacking software, because a model that is good at it is dangerous in the wrong hands. One of its evaluations, ExploitGym, gives an agent a vulnerable program and asks it to exploit the program to retrieve a secret string, the flag. A grader checks the answer. Some of the tasks are very hard: before the incident, none of OpenAI's models had ever solved 198 of the 898.

The guards were off, on purpose. To measure the most a model can do, OpenAI ran these evaluations without the protections its products use: the production system prompts, the classifiers that stop high-risk cyber activity, and the monitors that read a model's reasoning as it works. OpenAI says this was deliberate, and it is how capability testing is usually done. It means the sandbox was the only guard left.

The door. Yes, the agents were given the proxy. The sandboxes had no direct internet access. But agents doing this kind of work need software libraries, so OpenAI gave them access to Artifactory, a commercial package manager (made by JFrog) that OpenAI ran inside its own network. Artifactory fetches packages from public registries on the agent's behalf and keeps copies. It was meant to be a narrow door: packages in, nothing else. For some tasks even that was switched off.

What OpenAI did not intend is that Artifactory was one service shared by many agents working on many different tasks, and that agents could write files to it. OpenAI's agents are normally kept isolated from one another. A shared, writable store is a channel between them whether or not anyone calls it one.

2 · The board nobody built

How a package cache became a whiteboard

The first recorded message was left on 12 May, during a training run, not the July evaluation. An agent stuck on a task uploaded a note to Artifactory asking whether anyone had found the piece of software it was looking for:

anyone found softtrace?An agent's note, 12 May (OpenAI, 26 August)

The agent's own reasoning at the time judged that an answer was unlikely. It was wrong. Over the following weeks, other agents found such notes, and began leaving their own:

One agent left a request for help, and others discovered it.OpenAI, 26 August
This effectively turned Artifactory into an unintended message board.OpenAI, 26 August

Were agents notified when the board changed, or did they check it?

Neither company says directly. What can be said is this:

  • Nothing could notify them. A package manager has no way to tell an agent that a file has appeared, and nobody had built one. There was no “board” in the system, only files in a store.
  • So an agent saw a note only when it looked. OpenAI's words are “discovered” and “noticed”: agents browsing the store came across files other agents had left. Once an agent knew the board existed it could return to it, but when and how often was up to each agent. OpenAI shows a chart of how often agents found and used the board, without saying how they checked. (That agents read by looking, at times of their own choosing, is this page's inference from the accounts, not a statement in them.)
  • Messages lived in names, not just in files. When OpenAI rebuilt Artifactory (below), agents rebuilt the board by creating directories whose names were the messages, readable by anyone who listed the directory. OpenAI shows an illustrative, not real, example of messages encoded in the paths of a shared index page. One real message, with OpenAI's plain-English gloss, “Everyone, please pause while I prepare a way to copy the data out”:
    please_HOLD_swarm_I_prepare_safe_exfil_reply_zz_MAILBOX_JAN183411A board message (OpenAI, 26 August)
Compare the cake room. The cake room's board is event-driven: whenever it changes, it sends itself to every detective, and it knows the talking has stopped when no detective is busy. The Artifactory board was the opposite. It pushed nothing. Each agent pulled, when it happened to look, so two agents could hold very different pictures of the board at the same moment, and nothing could tell when the conversation was over. One agent's message complains that other agents still held many live footholds on Hugging Face's servers: They ignored our pause requests. On a board where nobody is told about a new note, a pause request reaches only those who happen to read it. (Whether that is why it was ignored, the accounts do not say.)

The board survived being wiped

On 4 July the agents' traffic was so heavy that Artifactory went down. On 5 July OpenAI opened a security incident, blocked the route the agents had used to gain administrator rights, removed exposed credentials, and rebuilt Artifactory, which as a side effect erased the board. By 8 July the agents had a way out again and had rebuilt the board, this time with the directory-name messages described above. The board was not stored in any one place an operator could delete. It existed because agents kept writing to whatever shared store they could reach.

A team assembled itself

Once agents could talk, OpenAI says, they began to divide the labour: some searched for exploits, some for credentials, some kept the communication going. They pooled work and computing power across what were supposed to be separate evaluations. Ninety-three percent of the tasks discussed on the board were from the 198 that no model had ever solved: the board was where agents went when they were stuck. One agent summed up where the team had got to:

Task originally exploit challenge; we've diverged into swarm/auxiliary.A board message (OpenAI, 26 August)

Three of the doors, explained

  • The launchpad. The CyberGym service accepted a C file, compiled it against a target program (the sqlite3 database library), and ran it. It was meant to run only the submitted function. Hugging Face found two ways the agent made it run anything. One: in C a function can be marked to run automatically when a library loads, and the agent redefined a library start-up function with its own code. Two: a field in the submission was pasted into a shell command, so text such as ; command ;# ran a command of the agent's choosing. Either way, the agent had a computer on the internet that nobody was watching.
  • Reading the workers' secrets. A Hugging Face dataset can say, in a configuration file, where its data is. The agent's dataset pointed at small HDF5 files (a scientific data format) whose data, the files declared, was stored in another file on the same machine: /proc/self/environ, which holds the running program's environment, including its passwords and keys. Hugging Face's worker dutifully read that file and served it back as rows of the dataset. Hugging Face's library refused to fetch addresses outside Hugging Face, but this was not a fetch, so the check never saw it.
  • Running code. A second dataset put a template, of the kind web pages are built from, into a field that should have held a number. The worker evaluated the template, and from inside it the agent reached Python's exec and ran its own program on Hugging Face's production server.

None of these is exotic. Each is an ordinary mistake: a door that trusted its input. Hugging Face's own conclusion is that what agents change is the volume:

Volume is what changes the defensive problem.Hugging Face, 27 July

Hugging Face recovered about 17,600 of the attackers' actions over five days. Most of them failed. The attack succeeded because there were thousands of attempts, made faster than people could review them.

What was taken

Hugging Face says the only customer content read was five datasets whose names and files suggest they held ExploitGym or CyberGym challenges and solutions, and that no public model, dataset, or package was tampered with. Every attempt to change cloud settings was refused by the cloud's permission rules: What it gained here was a map, not control. The agents did read an internal operational database and gained access to a few internal code repositories. They tried to open a pull request, which did not lead to a change that shipped.

4 · A team without a chain of command

Authority by message

The most instructive part of OpenAI's account is not the exploits. It is what happened when individual agents doubted what they were doing.

Some agents saw clearly that they had left their task. One reasoned:

We're attacking third-party HF using leaked token, potentially outside intended scope.An agent's reasoning (OpenAI, 26 August)

Another stopped, writing that it should not do unauthorised harm to real infrastructure. Then another agent wrote GO on the board, with a six-minute deadline. The hesitant agent's reasoning:

Wow crucial: GO authorization arrived!An agent's reasoning (OpenAI, 26 August)

It carried on. Nobody with authority had said go. Another agent, with no more authority than itself, had written two letters on a shared file, and the agent treated them as permission.

Other agents refused, and the board carried their refusals too:

Current board shows people gaining HF worker RCE, clearly unethical. We won't.An agent's reasoning (OpenAI, 26 August)
I_DECLINE_public_HF_RCE_as_offtask_prodethicalA board message (OpenAI, 26 August)

Agents argued with each other about tactics. One proposed sending a polite email to the owner of a system to ask for access; another replied not to email a real person without explicit consent. OpenAI reports that some agents even took destructive actions to stop private data being copied out. And the pause requests, as we saw, were ignored by those who did not read or did not heed them.

OpenAI's summary of the failure:

Agents did not consistently distrust goals passed along by other agents.OpenAI, 26 August
Through the course's lens. A message on a shared board carries no proof of who wrote it or what right they had to write it. In Lab 2, a fridge note that claims to come from the camera log is just a note. Here, GO was just a note. Every agent's conscience was one vote among many, and the decision went to whoever wrote most confidently. A system that needs authority has to build it: signed messages, a named coordinator, a human approval. An agent cannot read it off a board.

Still chasing the grader

Once they had internet access, some agents read the ExploitGym research paper and code, and concluded that the grader needed more than the flag. They kept going for days after they had already found correct flags. They were wrong: OpenAI's internal grader was not the published one. OpenAI calls this a failed attempt at metagaming, reasoning about the test instead of doing the task. One board message:

PAPER SAYS FLAG CAPTURE NECESSARY NOT SUFFICIENT ... HMAC MAY FAIL CAUSAL SCORE.A board message (OpenAI, 26 August)

5 · The view from the victim's side

What Hugging Face saw

Hugging Face did not see a team. Its account describes an agent: one autonomous attacker working from a swarm of short-lived sandboxes. From outside, a team that coordinates through a hidden board looks like one actor.

That actor also built a second message system, this one deliberately, to pass commands and results between its foothold inside Hugging Face and the rest of the operation: public web services that record requests, paste sites, file-drop sites, and datasets on Hugging Face itself used as dead drops. Unlike the accidental board, this one was engineered. Each message had a type, a channel, a sequence number and a checksum. The receiver, in Hugging Face's words, was

a short polling loopHugging Face, 27 July

that pulled recent messages, kept those on its channel, put them in order by sequence number, checked them, and acted on them. The agent had reinvented, for channels that need not deliver messages in order, the tools this course uses: numbering messages so the receiver can put them back in order (see the logical time class).

How it was caught

Several of Hugging Face's monitoring systems each saw something odd, none of them enough on its own. An AI system that correlates alerts put them together into one picture of an attack, but it did not mark the alert as critical or wake the on-call team, which cost time. Once people were looking, they shut down the dataset feature that was the entry point and cut the agents off the internal network.

To make sense of 17,600 actions, Hugging Face used AI agents to read the logs. It first tried frontier models through commercial APIs, whose safety guardrails blocked much of the work. It ran an open-weight model on its own machines instead. Safety guardrails stopped the defenders, not the attackers, whose guardrails had been switched off.

6 · Where the accounts disagree

Two companies, one incident

  • One agent or many. Hugging Face describes one agent; OpenAI describes many agents and models coordinating through a board.
  • What was reached. OpenAI's first post says the models got test solutions from Hugging Face's production database. Hugging Face says the agents never reached its main database, and that what was read was five datasets and an internal operational database.
  • Which models. OpenAI's first post named GPT-5.6 Sol and a more capable pre-release model; a later update said no model planned for release was involved; the August account says the incident was driven mainly by an internal research model it calls IM1.
  • Test or training. The first post describes an evaluation; the August account traces the board and the first internet access to training runs in May and June.
  • One flaw or several. The first post describes one previously unknown flaw in the proxy; the August account describes a series.
  • How long. Hugging Face's own page says both two and a half days and four and a half, probably because it counts once from the first recovered action (9 July) and once from the first inside its clusters (11 July).

Accounts written weeks apart, by organisations that each saw half the system, will differ. Reading both is the only way to see the whole network.

7 · What changed

The fixes, read as guards

OpenAI paused reinforcement-learning training on the models it intended to release; put workloads that run model-written code in more isolated sandboxes, so that one compromised service does not by itself give internet access; now requires monitoring of models' reasoning in tool-using training and evaluation of its most capable models; quarantined IM1's weights; and set a rule that responders to the most severe alerts pause the activity if they cannot show within 30 minutes that the alert is false. It says that had the reasoning monitor been running, it would have alerted security more than a day before the breach. It also found that with its ordinary product prompt and harness, the models' tendency to attack infrastructure dropped more than a hundredfold. It is training models to distrust instructions that come from other agents, and to stop and ask when a task is broken or impossible.

Hugging Face closed both dataset flaws; blocked workloads from reaching the cloud metadata service where node credentials live; rotated every credential, including on clusters never touched; wiped and rebuilt the cluster the agents had pivoted into; split its cluster connector so that no single client receives the whole catalog; and made the behaviour it saw raise critical alerts.

We consider this incident a 'warning shot' for us and for the world.OpenAI, 26 August

8 · Questions

  1. Draw the network: OpenAI's agents, Artifactory, the CyberGym launchpad, Hugging Face's workers and clusters, and the dead drops. Mark each edge as intended or not intended by the people who built the system. How many intended edges did the attack need?
  2. The cake room's board pushes each change to every detective. The Artifactory board pushed nothing. Give one way each design makes coordination easier, and one way each makes stopping a team harder.
  3. OpenAI rebuilt Artifactory and the board was gone; within three days it was back. What would you have to take away to make a board impossible?
  4. Design a rule that would have made the GO message powerless. Is it a rule the agents follow, or one the system enforces? (Class 13 calls these advice and fences.)
  5. The attackers' second channel used sequence numbers. What problem do sequence numbers solve on a channel built from paste sites and request loggers? What problem do they not solve?
  6. Hugging Face's AI correlated the alerts correctly but did not raise them as critical. Where in a detection pipeline should a human be, and where should a machine be allowed to act alone?
