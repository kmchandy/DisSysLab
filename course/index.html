Distributed Systems

This course is about building safe systems with multiple agents, some of which may be LLMs. The course emphasizes safety. We use temporal logic to prove that our algorithms do what they are specified to do, and we use systematic ways of testing multi-agent systems. We take particular care that the systems we create do not modify the environment in unintended ways.

The course has two aspects: (1) distributed system algorithms and (2) building multi-agent systems. Homework on algorithms is often either multiple choice or the design of small algorithms. The major part of the course is a project: you develop a multi-agent app that interests you. You can do the project on your own or in a team of two or three people.

The first lab homework, the one-dollar Tahoe, asks you to modify a network of agents and to investigate problems that may arise by prompt injection.

One idea: safety

The thread through every class, lab and the project.

A system is safe if nothing bad happens, whatever any one agent does. A language model is an agent whose behaviour we cannot specify exactly: it can be wrong, it can be talked into things, and the same question can get a different answer tomorrow. So we do not try to make each model safe. We design the network around the models so that the system is safe even when one of them is not. Three habits, used all term:

Specify

Say exactly what must never happen, and what must eventually happen. Temporal logic is the language for both.

Structure

Build the network so that a bad message cannot travel far: a contract on what each agent takes and gives, checked by code on every message; a guard before anything that acts; a fence around what an agent can reach; a person's approval for what cannot be undone.

Evidence

Prove what can be proved: the system is safe if every agent keeps its contract (rely and guarantee). Test the rest: attack your own system, many times, and report how often the attack succeeds.

Each class below names the safety question it answers. The algorithms are the ones that make the structure trustworthy: they are how a system notices that it is stuck, recovers from a failure, agrees when an agent halts or lies, and shares a resource without harm.

  2. Global snapshots, rollback and recovery

    Safety question. When something goes wrong, can we record a consistent state of the whole system, and go back to it?

    Open

  3. Logical time, termination and deadlock detection

    Logical clocks, snapshots at a logical time, vector clocks, and termination detection. Deadlock detection not written yet.

Part 3What agents know, and what they may do

  1. What Agents Know

    “Agent X knows P”: a formal definition of knowledge.

    Safety question. What can an agent leak? Knowledge travels only along paths of messages, so an agent that was never sent a secret cannot reveal it. This is the reason to give each agent only what it needs.

    Open

  2. Lab 2: Contracts, fences and approval

    What can go wrong, and the structures that limit it.

    • Prompt injection: a web page, an email or a customer's message that tells the agent what to do. Some inputs are adversarial, as in the Byzantine generals problem.
    • The quarantined reader: the agent that reads untrusted text passes on only bounded fields (one of a few values, a number in a range), so no instruction can reach the agents that act.
    • Permissions and sandboxing: what an agent may read, write, run or fetch, and why the default should be “no”.
    • Hooks: fixed code that runs before or after each tool call to block, log or check actions — a rule the agent cannot be argued out of.
    • Human approval: which actions need a person to approve them.
    • Skills and MCP connectors: packaged instructions an agent loads, and the connectors through which it reaches external tools and data: the trust boundary each one creates.

    Safety question. If an agent is compromised, what is the most it can do?

Part 4Agreement when agents fail

  1. Distributed consensus: The FLP theorem

    Agents propose values and must agree on one: validity, agreement and termination. Why no deterministic algorithm can guarantee all three if even one agent may halt — the FLP theorem.

    Safety question. What can no design guarantee? Knowing the limit tells you which promise you are giving up.

    Open

  2. The Paxos algorithm: serializing transactions

    Safety question. When several agents update shared state, how do we keep it from being corrupted?

    Open

  3. The Paxos algorithm

    Safety question. How do agents agree when some may stop or be slow? Paxos never lets two agents decide different values, whatever the timing.

    Open

  4. Lab 3: Agent SDK, managed agents

    • The agent loop: model, tools, results, repeat; building one with the Agent SDK.
    • Subagents and parallel agents: orchestrator and workers, fan-out and fan-in.
    • Context isolation: a subagent knows only what it is sent — what agents know.
    • Termination: when is a swarm of subagents done, and how does the orchestrator know? Termination detection again.
    • Failures: timeouts, retries, and actions that are safe to repeat; checkpointing a long run and resuming it — global snapshots and recovery.
    • Budgets: limits on rounds, calls and cost, so that a loop cannot run away.
    • Scheduled and long-running agents.

    Safety question. When an agent fails halfway, is it safe to try again? An action that cannot be repeated safely, such as paying or sending, needs a design that remembers it was done.

    Not written yet

Part 5Agreement when agents lie

  1. Byzantine consensus

    Consensus when agents may lie. Why majority voting fails, how signed messages help, and why the algorithm can stop after t+1 rounds — with a figure in which you choose the faults.

    Safety question. An agent that has been prompt-injected is a Byzantine agent: it says whatever its attacker wants. How many such agents can a system tolerate?

    Open

  2. Cryptography and cryptocurrency

    Hash functions, commitments, search puzzles, block chains, Merkle trees and digital signatures — every hash on the page computed live in your browser.

    Safety question. Who sent this message, and has it been changed on the way?

    Open

  3. Bitcoin

    Goofycoin, Scroogecoin and the double-spending problem; then consensus without a trusted party: proof of work, the longest chain, incentives and attacks, and how Bitcoin is engineered.

    Safety question. Can agents that do not trust one another, and act in their own interest, still agree?

    Open

  4. Lab 4: Agent collaboration

    • Agreement among LLMs: voting, debate, and a judge agent. When does majority voting help, and when does it fail? — the Byzantine generals.
    • Correlated errors: three models that agree may share the same blind spot. Agreement is not correctness; compare a panel of one model family with a panel of three, on questions whose answers are known.
    • Shared state: a store that agents read and write, and the races that follow — Paxos and serializability.
    • Message structure: structured outputs as a fixed message format between agents.
    • Evaluation: testing nondeterministic agents with repeated runs, scoring and regression checks. A safety claim about a model is a rate, not a yes or no.
    • Observability and audit: traces, costs and token budgets per agent; from a run's records, find the agent that introduced an error, and decide what should and should not have been recorded.

    Safety question. When should a system trust what its agents agree on?

The project

The major part of the course.

You build a multi-agent app that interests you, and you make the case that it is safe. The case has three parts, the three habits above:

  1. What must never happen, and what must eventually happen, stated precisely enough that someone else could check it.
  2. How your network prevents it: which contracts, guards, fences and approvals, and where they sit in the network.
  3. The evidence: what you proved, the attacks you tried, how many times, and how often they succeeded.
