Logical Time and Termination Detection

Logical clocks, vector clocks, and detecting that a computation has ended

This page assumes

A computation is drawn as a dataflow graph: a horizontal line for each agent, a dot for each event, and an arrow for each message (see Computations and Data Flow). Channels are first-in-first-out. A cut splits the events into a past and a future, with every agent's past events before its future events. A cut is consistent when every message received in the past is sent in the past, and then the states at the cut form a global snapshot (see Global Snapshots).

1. The Problem: Why Logical Clocks?

The problem is to assign timestamps to events so that [past(T), future(T)] is a consistent cut, where past(T) is the set of events with timestamps T or less and future(T) is the set of events with timestamps greater than T.

past(T) and future(T)
past(T) = {e | t(e) ≤ T}    future(T) = {e | t(e) > T}

For a number T, the events with timestamps at most T are in the past at T, and the others are in the future.

A simple solution, which is easily proved correct is:

Logical clock
t(e) < t(e′) for every edge (e, e′) of the dataflow graph

The algorithm

When an agent sends a message in an event it puts the event timestamp on the message. The timestamp t(e) of an event e is larger than the timestamp of the previous event ep at that agent and the timestamp t(es) of the message (if any) that it receives in the event.

t(e) > max(t(ep), t(es))

A common choice is t(e) = max(t(ep), t(es)) + 1.

Check yourself

In Figure 1, t(b3) = 4 and t(c5) = 6. Which of these are possible timestamps for b4? Pick all that apply.

The algorithm requires only t(b4) > max(t(b3), t(c5)) = max(4, 6) = 6, so 7, 8 and 9 are all possible. Adding 1 is a convention, not a requirement. Figure 1 uses it and gives t(b4) = 7.

2. A snapshot at logical time T

Snapshot at logical time T
local state: after the last event with t ≤ T, before the first with t > T

Each agent records its local state at the boundary between its past and its future. An agent v starts recording the messages it receives on channel (u, v) when it records its local state, and stops when it receives on that channel a message with timestamp greater than T. That message is not recorded. The state of channel (u, v) is the sequence of messages recorded.

The message with timestamp greater than T plays the role of the marker in the marker algorithm. The messages v records are exactly those sent in the past and received in the future: they are received after v's snapshot, and, because the channel is first-in-first-out, they are sent before the first message from u with a timestamp greater than T. The algorithm requires every agent to send messages on all its output channels with timestamps greater than T.

3. Vector clocks

Specification of a vector clock
t(e) < t(e′) ≡ (path from e to e′)

Assign timestamps to events so that t(e) is less than t(e′) exactly when there is a path from e to e′ in the dataflow graph.

The vector clock algorithm

The algorithm is straightforward. Each agent j keeps a vector tj of length n where n is the number of agents.

Vector timestamps For an event e at an agent j, t(e) = [n0, n1, …] exactly when
  1. for k different from j, nk is the number of events at agent k with a path to e, and
  2. nj is the number of events at agent j with a path to e, counting e itself.
Check yourself

With agents A, B, C, event b3 of Figure 2 sends m5 with timestamp [2, 4, 0]. Event a3, the previous event of A, has timestamp [4, 0, 2]. What is the timestamp of a4, which receives m5?

max([4, 0, 2], [2, 4, 0]) + [1, 0, 0] = [4, 4, 2] + [1, 0, 0] = [5, 4, 2]. Check it in Figure 2.
Order on vectors
n ≤ m ≡ (∀ j : nj ≤ mj)    n < m ≡ (n ≤ m) ∧ (n ≠ m)

Two vectors can be unordered: neither [1, 0] ≤ [0, 1] nor [0, 1] ≤ [1, 0].

Vector clock algorithm The algorithm is identical to the logical clock algorithm except that the timestamps are vectors.
t(e) = max(t(ep), t(es)) + uj

For an event e of agent j, t(e) is the element-wise maximum of the timestamp of j's previous event ep and, if e receives a message, the timestamp t(es) carried by the message; plus uj, the vector with a positive value (usually assumed to be 1) in element j and 0 elsewhere.

For example, with four agents: if event e of agent 1 has previous event with timestamp [3, 8, 2, 4] and receives a message carrying [10, 5, 3, 2], then t(e) = [10, 8, 3, 4] + [0, 1, 0, 0] = [10, 9, 3, 4].

Theorem Vector clocks meet the specification: for events e ≠ e′, t(e) < t(e′) exactly when there is a path from e to e′.
Proof

Induction on the sequence of events in the order of any computation.

4. Detection algorithms

A detection algorithm is run by the operating system (OS) to find out whether the client computation has some property -- for example, the client computation has terminated. These are properties that continue to hold until the OS takes action. For example, if a client computation is deadlocked then it remains deadlocked until the OS breaks the deadlock. In this section we focus on how the OS detects the condition and not about how the OS deals with the condition after it is detected. So, we assume that the condition is stable - if the condition holds in a state then it continues to hold for all succeeding states of all computations.

Detection algorithms are like snapshot algorithms. A detection algorithm takes time: its agents exchange messages while the client computation keeps executing. An algorithm to detect a property P has to deal with the possibility that ¬P holds when the detection algorithm starts, and while the detection algorithm is running the client computation makes P true. For example, the client computation may not be deadlocked when the deadlock detection algorithm starts but becomes deadlocked before the deadlock detection algorithm terminates.

Specification of a detection algorithm for stable P An algorithm to detect a property P must terminate and when it terminates it returns either that P holds or ¬P holds, where
  1. If condition P holds while the detection algorithm executes -- from when the detection algorithm starts to when it finishes -- then the algorithm returns that P holds
  2. If ¬P holds while the detection algorithm executes then the algorithm returns that ¬P holds.
  3. If ¬P holds when the detection algorithm starts and P holds when the detection algorithm finishes then then the algorithm returns either that P holds or that ¬P holds.

For example, to detect deadlock, the OS runs the deadlock detection algorithm repeatedly. This is because the client computation may have deadlocked after the last run of the detection algorithm determined that it hadn't deadlocked.

The generic solution Take a global snapshot. Each agent sends its local state and the states of its incoming channels to a detector agent. The detector puts them together and checks whether P holds in the snapshot.

Correctness proof If P holds in the detect state then P holds in all states reachable from the detect state because P is stable. There is a computation from the detect state to the end state and so the end state is reachable from the detect state. Therefore P holds in the end state.

If ¬P holds in the detect state then ¬P holds in all states that can reach the detect state because P is stable. There is a computation from the start state to the detect state and so the start state can reach the detect state. Therefore ¬P holds in the start state.

5. Termination detection

Consider a distributed system D in which each agent waits to receive messages on any of its incoming channels. (This type of system is different from the office used in DisSysLab where an agent can wait to receive messages on only one of its inputs.) Each agent in D is either active or idle. An active agent may send messages, and may become idle at any time. An idle agent sends no messages. An idle agent becomes active when it receives a message. Initially every agent is active and every channel is empty. A computation of D has terminated when every agent is idle and every channel is empty. Termination is stable -- after the computation terminates no idle agent can become active because all channels are empty, and messages cannot be added to channels because all agents are idle.

terminated ≡ all agents idle ∧ all channels empty

Specification The detection algorithm is part of the OS. Its specification is that the detection algorithm must finish, and the algorithm has a variable terminated, which is initially false, and must satisfy:

  1. Safety terminated ⟹ the client computation has terminated. The detector sets terminated to true only if the computation has terminated.
  2. Progress If the client computation has terminated when the detection algorithm starts then terminated is set to true when the detection algorithm finishes.

If the client computation has not terminated when the detection algorithm starts, but the client computation terminates before the detection algorithm finishes, then the value of terminated is unspecified -- it may be true or false.

A termination detection algorithm

For each channel X, the sending agent keeps a count Xs of the messages it has sent on X, and the receiving agent keeps a count Xr of the number of messages it has received on the channel. The number of messages in transit on X is Xs − Xr. The problem is that no agent has both numbers at the same instant. The sending agent cannot read Xr and the receiving agent cannot read Xs.

Consistent cuts and global snapshots allow us to use old values of Xs and Xr.

When an agent A becomes idle it sends a message to an OS agent called the detector. This message contains the value of Xs for every output channel X of agent A, and the value of Yr for every input channel Y of A. The message from A to the detector may be delayed by an arbitrary amount.

The detector has local variables X′s and X′r for every channel X. Let X be a channel from agent A to agent B. The detector's variable X′s is the value of Xs in the most recent message that the detector has received from A. Likewise, the detector's variable X′r is the value of Xr in the most recent message that the detector has received from B. Because message delays are arbitrary, it is possible that X′s ≠ Xs and X′r ≠ Xr. Nevertheless, the algorithm claims that the computation has terminated when, for all channels X, X′s = X′r.

Termination detection by counting
terminated := terminated ∨ (∀ X : X′s = X′r)

When an agent becomes idle, it sends its counts for all its channels to the detector. For each channel X the detector keeps X′s and X′r, the most recent counts it has received from the sender and from the receiver of X, initially 0 and −1. Each time it receives counts, it sets terminated to true if X′s = X′r for every channel X.

The values X′s and X′r are not the current counts. They are values the agents sent in the past, at different moments, and X′s − X′r need not be the number of messages in transit now. The initial values 0 ≠ −1 make sure the detector hears from both ends of every channel before it decides.

Why it is safe

Consider the points at which the agents sent the counts that the detector holds. If X′s ≥ X′r for every channel X, those points form a consistent cut: the receiver of X had received X′r messages, and because the channel is first-in-first-out these are the first X′r messages sent on X, all sent before the sender's point. At that cut every agent is idle, because agents send counts when they become idle, and every channel X holds X′s − X′r = 0 messages. So the computation had terminated at the cut, and termination is stable.

Progress. Every agent is active initially, so it becomes idle at least once and sends counts. After the computation terminates, each agent's last counts are its final counts, and in them every message sent has been received. When the detector has them all, X′s = X′r for every channel.

Check yourself

Both agents have become idle and reported, and the detector holds C′s = 3, C′r = 1, D′s = 2, D′r = 2. Should it conclude that the computation has terminated?

No. At the cut of the two reports, channel C held 3 − 1 = 2 messages. When B receives them it becomes active again. A detector that only checked “every agent has reported idle” would make exactly this mistake. Figure 4's Play the example passes through this state.

Notes

Logical clocks are due to Lamport, “Time, clocks, and the ordering of events in a distributed system” (1978). Vector clocks were introduced independently by Fidge and by Mattern in 1988. The snapshot at a logical time, with markers replaced by messages carrying timestamps, is a variant of the Chandy–Lamport snapshot algorithm (1985). Detecting termination by counting messages is in the spirit of Mattern's counting algorithms (1987); Dijkstra and Scholten (1980) and Francez (1980) gave early termination detection algorithms.
