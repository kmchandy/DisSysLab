Logical Time and Termination Detection

Logical clocks, vector clocks, and detecting that a computation has ended

This page assumes

A computation is drawn as a dataflow graph: a horizontal line for each agent, a dot for each event, and an arrow for each message (see Computations and Data Flow). Channels are first-in-first-out. A cut splits the events into a past and a future, with every agent's past events before its future events. A cut is consistent when every message received in the past is sent in the past, and then the states at the cut form a global snapshot (see Global Snapshots).

1. The Problem: Why Logical Clocks?

The problem is to assign timestamps to events so that past(T), future(T) is a consistent cut where past(T) is the set of events with timestamps T or less, and future(T) is the set of events with timestamps greater than T.

past(T) and future(T)
past(T) = {e | t(e) ≤ T}    future(T) = {e | t(e) > T}

For a number T, the events with timestamps at most T are in the past at T, and the others are in the future.

A simple solution, which is easily proved correct is:

Logical clock
t(e) < t(e′) for every edge (e, e′) of the dataflow graph

The algorithm

When an agent sends a message in an event it puts the event timestamp on the message. The timestamp t(e) of an event e is larger than the timestamp of the previous event ep at that agent and the timestamp t(es) of the message (if any) that it receives in the event.

t(e) > max(t(ep), t(es))

A common choice is t(e) = max(t(ep), t(es)) + 1.

Check yourself

In Figure 1, t(b3) = 4 and t(c5) = 6. Which of these are possible timestamps for b4? Pick all that apply.

The algorithm requires only t(b4) > max(t(b3), t(c5)) = max(4, 6) = 6, so 7, 8 and 9 are all possible. Adding 1 is a convention, not a requirement. Figure 1 uses it and gives t(b4) = 7.

2. A snapshot at logical time T

Snapshot at logical time T
local state: after the last event with t ≤ T, before the first with t > T

Each agent records its local state at the boundary between its past and its future. An agent v starts recording the messages it receives on channel (u, v) when it records its local state, and stops when it receives on that channel a message with timestamp greater than T. That message is not recorded. The state of channel (u, v) is the sequence of messages recorded. The algorithm requires every agent to send messages on all its output channels to ensure that all channel state are recorded.

The message with timestamp greater than T plays the role of the marker in the marker algorithm. The messages v records are exactly those sent in the past and received in the future: they are received after v's snapshot, and, because the channel is first-in-first-out, they are sent before the first message from u with a timestamp greater than T.

Check yourself

There is a bug in the algorithm. What happens to agent v if agent u never sends v a message with timestamp greater than T?

Agent v stops recording channel (u, v) only when a message with timestamp greater than T arrives on it. If none is ever sent, v never knows that the state it has recorded is complete, and the algorithm does not terminate. Compare the marker algorithm, in which every agent sends a marker on every outgoing channel. The fix is the same: the algorithm is correct if every agent keeps sending messages with increasing timestamps on every outgoing channel — null messages, if it has nothing else to send.

3. Logical time does not capture dependence

Say that event e′ depends on event e when there is a path from e to e′ in the dataflow graph. A logical clock guarantees

(path from e to e′) ⟹ t(e) < t(e′)

but not the converse. In Figure 1, t(c2) = 2 < 3 = t(a3), yet there is no path from c2 to a3: after c2, the only message C sends is m6, to B, and B sends nothing after receiving it. From timestamps alone, an agent cannot tell whether one event could have influenced another.

4. Vector clocks

Can timestamps capture dependence exactly?

Specification of a vector clock
t(e) < t(e′) ≡ (path from e to e′)

Assign timestamps to events so that t(e) is less than t(e′) exactly when e′ depends on e.

No numbers can do this, because any two numbers are ordered, while two events may be independent, with no path either way. So the timestamps are vectors, with one element per agent, ordered element by element:

Order on vectors
n ≤ m ≡ (∀ j : nj ≤ mj)    n < m ≡ (n ≤ m) ∧ (n ≠ m)

A vector n is at most m when it is at most m in every element. Two vectors can be unordered: neither [1, 0] ≤ [0, 1] nor [0, 1] ≤ [1, 0].

Vector clock algorithm
t(e) = max(t(ep), t(es)) + uj

For an event e of agent j, t(e) is the element-wise maximum of the timestamp of j's previous event ep and, if e receives a message, the timestamp t(es) carried by the message; plus uj, the vector with 1 in element j and 0 elsewhere. The initial event of agent j has timestamp uj.

For example, with four agents: if event e of agent 1 has previous event with timestamp [3, 8, 2, 4] and receives a message carrying [10, 5, 3, 2], then t(e) = [10, 8, 3, 4] + [0, 1, 0, 0] = [10, 9, 3, 4].

What a vector timestamp says If t(e) = [n0, n1, …] then, for every agent j, exactly nj events of agent j have a path to e, counting e itself: the first nj events on j's line.
Proof sketch

By induction over the events in the order they occur. The events with a path to e are e itself and the events with a path to ep or to es. The events of agent j with a path to any event form a prefix of j's line, so the union of two such sets is the longer prefix: the maximum. Adding uj counts e itself.

Theorem Vector clocks meet the specification: for events e ≠ e′, t(e) < t(e′) exactly when there is a path from e to e′.
Proof

Let e be the k-th event of agent j, so t(e)j = k. If there is a path from e to e′, every event with a path to e has a path to e′, so t(e) ≤ t(e′). Conversely, if t(e) ≤ t(e′) then t(e′)j ≥ k, so the first k events of j, e among them, have a path to e′. Finally, t(e) = t(e′) is impossible for e ≠ e′: it would give paths both ways, and the dataflow graph has no cycles.

Check yourself

With agents A, B, C, event b3 of Figure 3 sends m5 with timestamp [2, 4, 0]. Event a3, the previous event of A, has timestamp [4, 0, 2]. What is the timestamp of a4, which receives m5?

max([4, 0, 2], [2, 4, 0]) + [1, 0, 0] = [4, 4, 2] + [1, 0, 0] = [5, 4, 2]. Check it in Figure 3.

5. Detection algorithms

A detection algorithm is run by the operating system's agents to find out whether the client computation they manage has some property. The properties of interest are stable: once they hold, they hold for ever. Termination is one: a computation that has ended stays ended. Deadlock is another.

stable
stable(P) ≡ [P ⟹ AX P]

A predicate P on system states is stable when every step from a state in which P holds goes to a state in which P holds (see Temporal Logic, part 1).

A detection algorithm takes time: its agents exchange messages while the client computation keeps moving. So its specification is asymmetric between the state in which it starts and the state in which it ends.

Specification of a detection algorithm for stable P
returns “P” ⟹ P holds when it ends;   returns “¬P” ⟹ ¬P held when it started

If P holds throughout the run, the algorithm reports P. If ¬P holds throughout, it reports ¬P. If P becomes true during the run, it may report either.

The generic solution Take a global snapshot. Each agent sends its local state and the states of its incoming channels to a detector agent. The detector puts them together and checks P in the snapshot.

This works because P is stable. The snapshot is a state the system could have passed through between the start and the end of the algorithm. If P holds in it, P holds from then on, and so it holds at the end. If P does not hold in it, P did not hold at the start. A snapshot is static, which makes it much easier to analyze than the moving system. For particular properties, the generic solution can be streamlined, as the next section does for termination.

6. Termination detection

Active and idle agents
terminated ≡ all agents idle ∧ all channels empty

Each client agent is either active or idle. An active agent may send messages, and may become idle at any time. An idle agent sends no messages, and becomes active when it receives a message. Initially every agent is active and every channel is empty. The computation has terminated when every agent is idle and every channel is empty.

Termination is stable: no agent can become active again, because no message is in transit and no idle agent sends one. The detector has a variable terminated, initially false, and must satisfy:

  1. Safety invariant(terminated ⟹ the computation has terminated)
  2. Progress if the computation terminates, then terminated eventually becomes true

Counting messages

For each channel X, the sender keeps a count Xs of the messages it has sent on X, and the receiver keeps a count Xr of those it has received. The number of messages in transit on X is Xs − Xr. But no agent knows both numbers at the same moment.

Termination detection by counting
terminated := terminated ∨ (∀ X : X′s = X′r)

When an agent becomes idle, it sends its counts for all its channels to the detector. For each channel X the detector keeps X′s and X′r, the most recent counts it has received from the sender and from the receiver of X, initially 0 and −1. Each time it receives counts, it sets terminated to true if X′s = X′r for every channel X.

The values X′s and X′r are not the current counts. They are values the agents sent in the past, at different moments, and X′s − X′r need not be the number of messages in transit now. The initial values 0 ≠ −1 make sure the detector hears from both ends of every channel before it decides.

Why it is safe

Consider the points at which the agents sent the counts that the detector holds. If X′s ≥ X′r for every channel X, those points form a consistent cut: the receiver of X had received X′r messages, and because the channel is first-in-first-out these are the first X′r messages sent on X, all sent before the sender's point. At that cut every agent is idle, because agents send counts when they become idle, and every channel X holds X′s − X′r = 0 messages. So the computation had terminated at the cut, and termination is stable.

Progress. Every agent is active initially, so it becomes idle at least once and sends counts. After the computation terminates, each agent's last counts are its final counts, and in them every message sent has been received. When the detector has them all, X′s = X′r for every channel.

Check yourself

Both agents have become idle and reported, and the detector holds C′s = 3, C′r = 1, D′s = 2, D′r = 2. Should it conclude that the computation has terminated?

No. At the cut of the two reports, channel C held 3 − 1 = 2 messages. When B receives them it becomes active again. A detector that only checked “every agent has reported idle” would make exactly this mistake. Figure 4's Play the example passes through this state.

Notes

Logical clocks are due to Lamport, “Time, clocks, and the ordering of events in a distributed system” (1978). Vector clocks were introduced independently by Fidge and by Mattern in 1988. The snapshot at a logical time, with markers replaced by messages carrying timestamps, is a variant of the Chandy–Lamport snapshot algorithm (1985). Detecting termination by counting messages is in the spirit of Mattern's counting algorithms (1987); Dijkstra and Scholten (1980) and Francez (1980) gave early termination detection algorithms.
