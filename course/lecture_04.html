Distributed operating system algorithms

An operating system (OS) carries out actions on behalf of its client without changes to the execution of the client algorithm. For example, an OS algorithm takes repeated checkpoints of the client's execution. The execution of the client algorithm remains unchanged (except that it may run slower because the OS and client use the same resources) when the checkpoint algorithm runs.

The OS may use the same processes, threads, and queues that the client does. We build systems with an OS agent for every client agent. OS messages are trapped by the OS agent and not passed on to the client agents. Client agents never receive or send OS messages.

OS Managers

We will use OS agents that are not associated with any specific client. In many distributed OS algorithms we assume an OS systems-manager agent or a set of such agents that manage the entire client system. OS messages are exchanged between the OS systems-manager and the OS agents responsible for each client.

We begin with a simple algorithm that we will refine to make more efficient. In the simple global snapshot algorithm, the OS systems-manager sends messages to the OS client-managers to take local snapshots of their clients. When a client-manager completes taking its local snapshot it sends its local snapshot information to the systems manager. The systems manager then collates information from each client manager to form a global snapshot.

For brevity, when we describe OS algorithms we will use agent X instead of the longer, and correct, OS client-manager of agent X. The OS algorithm is independent of client computations, so while describing OS algorithms we need not distinguish the manager of an agent from the agent itself.

Messages that agents send to the systems manager

Assume that agents could take their local snapshots (i.e., record their own states) at the same instant. What messages do agents send to the systems manager?

Each agent sends a message to the systems manager with the agent's own local state and the sequence of messages it has placed on each of its outboxes and the sequence of messages it has received from each of its inboxes -- these are the messages that the agent sent and received in the past. For each connected outbox-inbox pair the systems manager determines the messages in transit: the messages sent in the past on that outbox, with the messages received in the past from the inbox removed. (We will see later that the entire sequence of messages need not be stored.)

The Global Snapshot

Each agent's clock can deviate by arbitrary amounts from the clocks of other agents. So if all agents take their local snapshots when their local clocks are at t the snapshots may not be taken at the same instant. In the simple algorithm, the systems manager sends messages to the agents. If each agent takes its local snapshot when it receives the message from the systems manager, the agents may still not take their local snapshots at the same instant.

An algorithm to determine a global snapshot is not instantaneous: it starts at some point and finishes at a later point.

The global snapshot Let S_init and S_fini be the states of the system at which the global snapshot algorithm starts and finishes, respectively. The global snapshot is a state S_snap of the system such that there is a computation from S_init to S_snap to S_fini.

Why is the global snapshot useful?

Checkpoint, rollback and recovery. In the event of a transient error the system can restart from the most recent checkpoint (a global snapshot) and continue execution from there.

Detecting stable properties. A stable property is one that if it holds at any point in a computation then it continues to hold thereafter. Examples of stable properties are that the system has terminated, or that a set of agents is deadlocked. Let P be a stable property. The problem is to develop an algorithm that detects whether P holds. A global snapshot answers it because of two facts:

  1. If P holds when the algorithm starts then P holds in the snapshot.
  2. If P holds in the snapshot then P holds when the algorithm terminates.

Both facts follow from the theorem below. By the theorem there is a computation from S_init to S_snap to S_fini, and P is stable in every computation of the system. So if P holds at S_init it still holds at S_snap, which is the first fact; and if P holds at S_snap it still holds at S_fini, which is the second.

Stability is doing real work here. The inbox of agent X is empty is not a stable property: it can be true at S_snap and false at S_fini, or false at S_init and true at S_snap. Of a stable property, a snapshot tells you something about the system now; of an unstable one, it tells you only that it held in some state the system may never have been in.

One way of detecting a stable property P is to take global snapshots repeatedly and check whether P holds in the snapshot.

Past and Future

When there are perfect clocks, the past at time t is obvious. Because agents don't take local snapshots at the same instant, we define past and future with respect to the points at which local snapshots are taken.

Past and future events An event at an agent is a past event exactly when it occurs before the agent takes its local snapshot. Events that are not past events are future events.

The Global Snapshot Theorem

The global snapshot theorem The points of local snapshots correspond to a global snapshot exactly when
every message received in the past is sent in the past.

Proof

The proof uses the theorem of lecture 3: Given a set of agent computations recorded in a system computation, all interleavings of agent computations in which each message is received only after it is sent are system computations.

Let agent computations be recorded during a system computation C. Construct an interleaving C' of agent computations as follows: in C' the relative ordering of past events is the same as in C, and the relative ordering of future events is also the same as in C, but every past event appears before every future one.

C' is a computation

Consider any message m, and the two events that send and receive it. There are four cases, and the hypothesis of the theorem rules out the only bad one.

  1. m is sent in the past and received in the past. Both events are past events, and in C' the past events keep the order they had in C — in which m was sent before it was received.
  2. m is sent in the past and received in the future. The send is a past event and the receive is a future event, and in C' every past event comes before every future one.
  3. m is sent in the future and received in the future. Both events are future events, and in C' the future events keep the order they had in C.
  4. m is sent in the future and received in the past. This is the only case in which C' would put a receive before its send — and it is exactly the case the hypothesis forbids, so it does not arise.

So every message in C' is received only after it is sent, and by the theorem of lecture 3, C' is a computation of the system.

C' passes through the recorded state

C' is a reordering of the events recorded during the algorithm, so C' starts at S_init and ends at S_fini. Consider the state of the system in C' after every past event and before every future one. Each agent has performed exactly its past events, so each agent's state is the state it recorded in its local snapshot. And a message is in transit in that state exactly when it was sent and not received among the past events — which is exactly what the algorithm records as in transit. So that state is S_snap, and C' is a computation from S_init to S_snap to S_fini.

The other direction

Conversely, suppose some message m is received in the past and sent in the future. Then S_snap is a state in which X has already received m and X' has not yet sent it. A message is received only after it is sent, so no computation of the system reaches such a state; in particular there is no computation from S_init to S_snap. The points of local snapshots therefore do not correspond to a global snapshot — which is the situation in Example 1.

A Global Snapshot Algorithm

Local snapshots

An agent takes its local snapshot by recording (1) its own state, (2) for each outbox, the sequence of messages it has placed on that outbox, and (3) for each inbox, the sequence of messages it has received from that inbox.

When an agent takes its local snapshot it sends this information to the OS systems-manager.

Global snapshot algorithms are based on this principle: select points at which agents take local snapshots so that messages received in the past are sent in the past.

When agents take local snapshots

  1. When an agent takes its local snapshot the agent puts a special message that we call a marker on each of its outboxes.
  2. When an agent receives a marker from any inbox, if the agent has already taken its local snapshot then the agent does nothing. If the agent has not taken its local snapshot then it does so and (from the previous rule) puts a marker on each of its outboxes.

A marker is an OS message. As in Figure 1, it is trapped by the OS agent that receives it and is never passed on to the client inside, so no client ever sees a marker and no client's computation is changed by the algorithm. Markers travel along the same connections as the clients' own messages — which is exactly why the queue argument below works.

Proof that messages received in the past are sent in the past

Let m be a message that agent X receives from inbox b in the past, and let X' be the agent that placed m on outbox b', where b' is connected to b. We show that m is sent in the past.

X receives m in the past, that is, before X takes its local snapshot. When an agent receives a marker it takes its local snapshot if it has not already done so, so X takes its local snapshot no later than the arrival of the marker on b. Therefore X receives m before the marker on b.

Outboxes, connections, and inboxes are queues — so messages are received from an inbox in the order in which they were placed in the outbox to which it is connected. Therefore X' placed m on outbox b' before X' placed the marker on b'. And X' puts a marker on each of its outboxes when it takes its local snapshot. So X' placed m on b' before it took its own snapshot, that is, m is sent in the past.

Starting the algorithm

The algorithm requires every agent to send its snapshot to the systems manager. The proof that messages received in the past are sent in the past requires that each agent takes its snapshot when or before it receives a marker.

The following mechanism can be used to start the algorithm: each agent takes its snapshot when its local clock reaches T, if the agent has not already taken its snapshot. This only requires that clock times increase forever; it does not require that clocks be synchronized.

Logical clocks

The snapshot algorithm never needed a clock. But the pictures in this class keep asking a question a clock would answer: given a computation, can we put a number on every event so that the numbers only ever increase along the arrows? Not real time — there is none to be had — but a logical time.

Logical timestamps Assign a number t(e) to every event e so that for every edge (e, e′) of the dataflow graph — every agent step and every message — t(e) < t(e′).

One consequence is the property this class has been circling: for any number t, every message received before t was sent before t. A cut taken at a logical time is a consistent cut, by construction.

Clocks that drift

Where do the numbers come from? Each agent has a clock, and no two clocks agree. Here X and Y have accurate ones, so for them a timestamp is simply the physical distance from the start. Z's clock is slow — it runs at half speed — and a slow clock would break the rule that time increases along every message: Z would stamp an event with a time earlier than the message that caused it.

So an agent does not merely read its clock. It sets it forward. If a message arrives carrying time 3.0 while Z's clock reads 2.3, Z moves its own clock to 3.1 and ticks on from there, slowly, until the next message pushes it again. The timestamp of an event is then always just what the agent's own clock reads; the clock is simply nudged whenever a message finds it behind. And the nudge is continuous — the clock sweeps up through 2.4, 2.5, 2.6 — which matters in a moment: it means that for every time t there is a point on every agent's line where that agent's clock reads t.

A snapshot at a logical time

Now put the two ideas together. Name a time, and every agent records its state at the moment its own clock passes that time. There is always such a moment, because a clock moves continuously, even while it is being set forward. No coordination, no markers — and what comes out is a consistent cut, because time only ever increases along a message.

Deadlock, which is termination of a part

A deadlocked system is usually not a system that has stopped. It is one where most of the machinery is humming along and some subset of it has quietly died: a set of agents each waiting for a message that only another member of the set could send. Nothing in any one agent's own state says so. Each of them sees only that it is waiting, which is the most ordinary thing in the world.

Here is the smallest example worth drawing. Three agents in a ring, each with two inboxes and two outboxes, each running this program: 

loop:
    t = receive(in1)     # a token, from the agent behind me in the ring
    m = receive(in2)     # a data item, from the pipeline
    send(out1, t)        # pass the token on, round the ring
    send(out2, m)        # pass the data on, down the pipeline

Each in1 is fed by the previous agent's out1, so channel 1 closes into a ring: u → v → w → u. Each in2 is fed by the previous agent's out2, so channel 2 is a straight pipeline: src1 → u → v → w → snk1. A second strand, src2 → x → snk2, runs alongside and shares nothing with the first, so that there is always something on the screen that the trouble does not touch.
