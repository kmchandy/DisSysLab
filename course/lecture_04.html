Distributed operating system algorithms

An operating system (OS) carries out actions on behalf of its client without changes to the execution of the client algorithm. For example, an OS algorithm takes repeated checkpoints of the client's execution. The execution of the client algorithm remains unchanged (except that it may run slower because the OS and client use the same resources) when the checkpoint algorithm runs.

The OS may use the same processes, threads, and queues that the client does. We build systems with an OS agent for every client agent. OS messages are trapped by the OS agent and not passed on to the client agents. Client agents never receive or send OS messages.

OS Managers

We will use operating systems agents that are not associated with any specific client. In many distributed OS algorithms we assume an OS systems-manager agent or a set of such agents that manage the entire client systems. OS messages are exchanged between the OS systems-manager and the OS agents responsible for each client.

We begin with a simple algorithm that we will refine to make more efficient. In the simple global snapshot algorithm, the OS systems-manager sends messages to the OS client-managers to take local snapshots of their agents. When a client-manager completes taking its local snapshot it sends its local snapshot information to the systems manager. The systems manager then collates information from each client manager to form a global snapshot.

For brevity, when we describe OS algorithms we will use agent Xinstead of the longer, and correct, OS client manager of agent X. We don't consider the client agent's computations and so we don't need to distinguish the manager of agent from the agent itself.

The Global Snapshot

Let S_init and S_fini be the states of the system at which the global snapshot algorithm starts and finishes, respectively. The global snapshot is a state S_snap of the system such that there is a computation from S_init to S_snap to S_fini.

Why is the global snapshot useful?

Checkpoint, rollback and recovery
In the event of a transient error the system can restart from the most recent checkpoint (a global snapshot) and continue execution from there.

Detecting stable properties
A stable property is one that if it holds at any point in a computation then it continues to hold thereafter. Examples of stable properties are that the system has terminated, or that a set of agents is deadlocked. Let P be a stable property. A problem is to develop an algorithm that detects whether P holds.

  1. If P holds when the algorithm starts then P holds in the snapshot.
  2. If P holds in the snapshot then P holds when the algorithm terminates.

One way of detecting a stable property P is to take global snapshots repeatedly and check whether P holds in the snapshot.

The Global Snapshot Theorem

Assume that each agent takes its local snapshot (i.e. records its own state) at some point in a computation. The points of local snapshots correspond to a global snapshot exactly when for every connection from outbox b of agent X to inbox b' of agent X': the number of messages received by X' from inbox b' is less than or equal to the number of messages placed in outbox b by agent X.

Proof

The proof follows from the theorem of lecture 3: Given a set of agent computations recorded in a system computation, all interleavings of agent computations in which each message is sent before it is received are system computations.

Let agent computations be recorded during a system computation C. Define all events at an agent before the agent takes its local snapshot as past events, and the other events at that agent as future events. Construct an interleaving C' of agent computations as follows: In C', the relative ordering of past events is the same as in C, and the relative ordering of future events is also the same as in C, but past events appear before future ones. The interleaving C' satisfies the conditions of the theorem: each message is sent before it is received.

States of channels in global snapshots

The global snapshot theorem says that the points of local snapshots correspond to a global snapshot exactly when no message sent in the future is received in the past. (Equivalently, all messages received in the past are sent in the past. And all messages sent in the future are received in the future.)

A message in transit at a point in a computation is a message that has been placed in an outbox and not yet removed from the inbox to which the outbox is connected. A message in transit may be in an outbox, or in the channel connecting the outbox to an inbox, or in an inbox. Define messages in transit in a snapshot as messages sent, and not received, in the past.

In the example (Figure 10), x1, y1, y2, z1, z2, z3 are past events and the other events are future events. The message sent at z1 and received at x2 is in transit in the snapshot because it is sent in the past and not received in the past. Likewise, the message sent at z2 and received at x3 is in transit. By contrast, the message sent at y2 and received at z3 is not in transit because it is sent and received in the past. Likewise, the message from y3 to x4 is not in transit because it is sent and received in the future.

The global snapshot algorithm

The algorithm uses the fact that outboxes, channels connecting outboxes to inboxes, and inboxes are queues. So if m is placed in the outbox before m' then m is received before m'.

When agents take local snapshots

  1. When an agent takes its local snapshot (i.e. records its own state) the agent puts a special message that we call a marker on each of its outboxes.
  2. When an agent receives a marker from any inbox it takes its local snapshot if it hasn't already done so. Note that by the previous rule it puts markers on its outboxes when it takes its local snapshot.

How agents record messages in transit

Assume that each message has a unique id. So when a message m is received from an inbox we can uniquely identify the event in which m is placed in the outbox to which the inbox is connected. Assume that each agent keeps track of the sequence of messages it places on each outbox and the number of messages it receives from each inbox. When an agent sends a message to the OS manager the message includes this information. So for each agent X and for each outbox b of X the OS manager gets the sequence of messages sent on b before X takes its snapshot -- these are the messages sent in the past through outbox b. Let this outbox be connected to inbox b' of agent X'. So the OS manager has the number of messages that were received on b' in the past. The sequence of messages in transit, sent though b to b', in the snapshot are the past messages placed in b excluding the number of messages received in b' in the past.

Correctness of the snapshot algorithm

We show that messages sent in the future (i.e. after a marker is sent on a channel) are not received in the past (i.e. before the marker is received on the channel).

Consider any connection from an outbox b of an agent X to an inbox b' of an agent Y. Let m be a message that X places in outbox b in the future — that is, after X has taken its local snapshot. By the first rule X put a marker in outbox b when it records its own state; so the marker is placed in the oubox before m is. Because the connection delivers messages in order, Y receives the marker before it receives m. By the second rule Y takes its local snapshot when the marker arrives. So Y records its state before m arrives. Hence m is received in the future.
