Distributed perating system algorithms

An operating system (OS) carries out actions on behalf of its client without changes to the execution of the client algorithm. For example, an OS algorithm takes repeated checkpoints of the client's execution. The execution of the client algorithm remains unchanged (except that it may run slower because the OS and client use the same resources) when the checkpoint algorithm runs.

The OS may use the same processes, threads, and queues that the client does. We build systems with an OS agent for every client agent. OS messages are trapped by the OS agent and not passed on to the client agents. Client agents never receive or send OS messages.

The state the snapshot records

Prose to come. The algorithm begins when the first agent records and finishes when the last one does. The Global Snapshot

Let S_init and S_fini be the states of the system at which the global snapshot algorithm starts and finishes, respectively. The global snapshot is a state S_snap of the system such that there is a computation from S_init to S_snap to S_fini.

Why is the global snapshot useful?

Checkpoint, rollback and recovery
In the event of a transient error the system can restart from the most recent checkpoint (a global snapshot) and continue execution from there.

Detecting stable properties
A stable property is one that if it holds at any point in a computation then it continues to hold thereafter. Examples of stable properties are that the system has terminated, or that a set of agents is deadlocked. Let P be a stable property. A problem is to develop an algorithm that detect whether P holds.

  1. If P holds when the algorithm starts then P holds in the snapshot.
  2. If P holds in the snapshot then P holds when the algorithm terminates.

One way of detecting a stable property P is to take global snapshots repeatedly and check whether P holds in the snapshot.

The Global Snapshot: past and future events

Assume that each agent takes its local snapshot (i.e. records its own state) at some point in a computation. Define all events at an agent before the agent takes its local snapshot as past events. Similarly, define all events at an agent after the agent takes its local snapshot as future events. Define the messages at the snapshot as messages sent in the past and received in the future. The snapshot is a global snapshot exactly when there is no message sent in the future and received in the past. (Equivalently, all messages received in the past are sent in the past. Or, all messages sent in the future are received in the future.)

In the example, x1, y1, y2, z1, z2, z3 are past events and the other events are future events. The message sent at z1 and received at x2 is a message in the snapshot because it is sent in the past and received in the future. Likewise, the message sent in z2 and received in x3 is also in the snapshot. By contrast, the message sent at y2 and received at z3 is not in the snapshot because it is sent and received in the past. Likewise, the message from y3 to x4 is not in the snapshot because it is sent and received in the future.

When agents take local snapshots

  1. When an agent takes its local snapshot (i.e. records its own state) the agent puts a special message that we call a marker on each of its outboxes.
  2. When an agent receives a marker from any inbox it takes its local snapshot if it hasn't already done so. Note that by the previous rule it puts markers on its outboxes when it takes its local snapshot.
