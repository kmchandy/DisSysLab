Sharing Resources

Priority by time, or by an order on resources

Agents often need exclusive use of several resources at once: a set of files, a set of locks, a set of devices. This class gives two simple ideas for sharing resources fairly. The first decides conflicts by time: the agent that started waiting earliest wins. The second puts the resources in order and makes every agent ask for them in that order. As in the dining philosophers, the arguments are informal, and the animations show why they hold.

1. The problem

Our example has three resources, which we call tea, milk and coffee; think of them as three files. Each resource has a manager, an agent that hands it out and keeps a queue of requests for it. The other agents, here Maya and Liu, go round a cycle of three states, which Chandy and Misra called

  • tranquil: the agent holds no resources, and may stay tranquil for ever;
  • thirsty: the agent wants a set of resources, any nonempty set, and waits for them;
  • drinking: the agent holds all the resources it wanted and uses them, for a finite time. Then it returns them to their managers and becomes tranquil.

A thirsty agent sends a request to the manager of each resource it wants; a manager sends a resource to an agent, and the agent later sends it back. Messages take an arbitrary but finite time. Each resource is a token: it is always in exactly one place.

Specification

Safety. A resource is held by at most one agent at a time.

Progress. Every thirsty agent drinks eventually.

The dining philosophers are the special case in which every agent always wants the same resources, the forks it shares with its neighbors.

2. What can go wrong

Deadlock

Suppose agents ask for their resources one at a time, in any order, and managers serve requests first come, first served. Maya wants tea and then milk; Liu wants milk and then tea.

Starvation

Deadlock comes from waiting in a cycle. A priority breaks the cycle: a manager can take a resource back from a lower-priority agent that is still thirsty, and give it to a higher-priority one. Give each agent a fixed number, its id, and let the higher id win. Will that work? No: an agent with a high id can win every conflict, for ever.

The priority of an agent that loses a conflict must rise relative to the winner. The two ideas that follow do this in different ways.

3. Idea 1: the agent that waited longest wins

Each agent has a local clock. The clocks need not agree; all we need is that every clock ticks forward for ever, so that it eventually passes any given time. When an agent becomes thirsty it reads its clock and takes a stamp (t, id). Stamps are compared first by t, and when the clock readings are equal, by id: the smaller id wins the tie. So any two stamps can be compared, and no two are equal. The earlier stamp has the higher priority.

The algorithm with stamps
  1. A thirsty agent sends a request, carrying its stamp, to the manager of every resource it wants, all at once.
  2. A manager keeps its requests in order of stamp, and sends a free resource to the earliest request.
  3. If a request arrives that is earlier than the stamp of the agent holding the resource, the manager asks that agent to return it.
  4. An agent asked to return a resource returns it if it is thirsty; its request goes back into the manager's queue. If it is drinking, it keeps the resource until it finishes.
  5. An agent that holds everything it wants drinks, and returns everything when it finishes.

Go back to Figure 3 and choose Priority by time. Each time Liu becomes thirsty again, his new stamp is later than Maya's, so the manager no longer takes milk away from her: she drinks, and they take turns.

Safety, informally

A resource is a token: managers and agents pass it on, but never copy it. So at most one agent holds it.

Progress, informally

Take a thirsty agent with stamp (T, id). The argument has two parts.

Part 1: every clock passes T, and stays past it (Figure 4). Clocks tick forward and never go back. So after a while every new request has a stamp later than T, and only finitely many requests have stamps up to T.

Part 2: the requests with stamps up to T run out (Figure 6). Look at the earliest of them that is still waiting. Every manager it asks puts it first, and takes the resource back from any later agent that is only thirsty; an agent that is drinking gives the resource back when it finishes. So the earliest request gets everything it wants, and drinks. Then the next earliest does, and so on, until our agent drinks.

4. Idea 2: an order on resources

The second idea needs no clocks. Give the resources a fixed order, here tea > milk > coffee. An agent asks for the resources it wants one at a time, highest first, and asks for the next only when it holds all the higher ones. For example, an agent that wants coffee and tea asks for tea, and asks for coffee only once it has tea. Managers serve requests first come, first served, and never take a resource back.

Why no one waits for ever, informally

A thirsty agent waiting for a resource r holds only resources above r, because it asks highest first. So an agent never waits for a resource higher than one it holds, and a cycle of agents each waiting for the next is impossible.

Go up the order, starting from the lowest resource, coffee. An agent holding coffee waits for nothing below it, so it has everything it wants: it drinks and returns coffee, and since the queue is first come, first served, everyone waiting for coffee gets it in turn. An agent holding milk waits at most for coffee, which it gets; so it drinks and returns milk, and everyone in the milk queue gets milk in turn. Then the same for tea. So every thirsty agent drinks.

The dining philosophers algorithm is a third way: there the priority between two neighbors is stored in the fork they share, and changes when one of them eats.

6. Key ideas

  1. Priority among agents in conflict. Some agents win and others lose. Winning must be fair: every agent that wants to win wins eventually.
  2. Tokens. An agent that holds a token knows that no other agent holds it. Resources are tokens.
  3. Dynamic priorities. Priorities can come from an order on resources, from stamps made of clock readings and ids, or from an acyclic graph of agents that changes as they act, as in the dining philosophers.
